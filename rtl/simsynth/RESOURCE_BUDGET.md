# 存储与资源核算（多声部：吉他 / 钢琴）

> 口径：当前 RTL（逐字段 Q + 32 位尾数，`modal_step_pkg`；`modal_voice_top` 用**多槽存储 +
> 状态 ping-pong**）。器件 **GW5AST-LV138FPG676AES**：138240 逻辑、139140 FF、
> 340 BSRAM（18 Kbit/块）、298 DSP；48 kHz / 100 MHz ⇒ 每采样 **2083 拍**。

## 1. 一个模态要存什么

| 内容 | 位宽 | 位 | 字节 |
|---|---|---|---|
| 系数 `a11 a12 a21 a22 gq gv wo` | 7 × 32 | 224 | 28 |
| 状态 `q`、`q̇`（ping-pong 两份） | 2 × 32 × 2 | 128 | 16 |
| **合计 / 模态** | | **352** | **44** |

- **系数没有元数据**：移位量是逐字段的编译期常量（`SH_A11…SH_WO`），记录里不存；
  旧格式（24 位尾数 + 每条目 6 位移位）每模态 274 位且精度差 78 倍。
- 状态要两份是因为 `modal_voice_top` 做 ping-pong：引擎读"旧"、写"新"，每帧末交换。
  这样"顶层可写的那一份"永远是引擎下一帧要读的那块（note-on 清零、直接往 q 上加激励都只写它），
  而且引擎永远不写自己正在读的阵列。代价 8 B/模态。

## 2. 两种乐器的总量

| | 吉他 | 钢琴 |
|---|---|---|
| 每声部弦数 / 每弦模态数 | 1 / 20 | 2 / 40 |
| **模态 / 声部** | **20** | **80** |
| 16 槽：系数 + 状态 | 16 × 20 × 44 B = **13.75 KiB** | 16 × 80 × 44 B = **55 KiB** |
| 32 槽：系数 + 状态 | 27.5 KiB | 110 KiB |

激励/结果缓冲：`x` 每声部每采样 32 位（深 64 ⇒ 256 B/声部）；
`y` **不分声部存**——顶层每帧把各声部的 Σ wo·q 加起来，只存"每采样一个"和（深 64 ⇒ 512 B 总共）。

| | 16 槽 | 32 槽 |
|---|---|---|
| `x`（16/32 槽 × 64 × 32 位） | 4 KiB | 8 KiB |
| `y_out`（64 × 64 位） | 0.5 KiB | 0.5 KiB |
| 小计 | 4.5 KiB | 8.5 KiB |

含缓冲的总量（BSRAM 按本设计实测 **≈823 B/块** 折算，见第 3 节）：

| | 16 槽 | 32 槽 |
|---|---|---|
| 吉他 | 18.25 KiB ≈ **23 块**（7%） | 36 KiB ≈ **44 块**（13%） |
| 钢琴 | 59.5 KiB ≈ **72 块**（21%） | 118.5 KiB ≈ **145 块**（43%） |

> 块长的选择直接影响这块：深 16 时 x/y 只有 3 / 6 KiB。
> 若激励由顶层实时算出、不落 RAM，还能再省一半。

## 3. 8 声部：两种架构的实测对比

同器件、同 `syn + pnr` 流程、100 MHz 约束、`N_MODES = 48`、`DEBUG_PORT = 0`，
**两边都已修掉 `coeff_t` 结构体阵列的 FF 回退**（否则比的是"谁的 bug 更贵"）。

| 指标 | `modal_bank_ram` × 8 实例 | **7 乘法器共用引擎 × 1** |
|---|---|---|
| 声部组织 | 每声部一个 bank（存储与引擎绑死），8 个并行 | 1 个引擎时分 8 个槽，存储在顶层 |
| Logic | 13104 | **1645**（8.0× 少） |
| Register | 6129 | **846**（7.2× 少） |
| BSRAM | 192 / 340（56%） | **28 / 340**（8%，6.9× 少） |
| DSP | 32（16 × MULT27X36） | **28**（14 × MULT27X36） |
| 每采样拍数（8 声部 × 48 模态） | 530 | **约 480**（8 × (56+4)） |
| **PnR Fmax（100 MHz 约束）** | **74.8 MHz**（slack −3.374 ns，未收敛） | **100.9 MHz**（slack +0.085 ns，收敛） |
| 每声部摊薄：Logic / Reg / BSRAM | 1638 / 766 / 24 | **206 / 106 / 3.5** |
| 关键路径 | 乘 → 64 位舍入 → **6 级桶形移位** → 累加（13.4 ns） | BSRAM 读出 → 状态 2 选 1 → 乘法器输入（9.9 ns） |

**为什么差距这么大**

1. `modal_bank_ram` 一个 bank 只有 48 个模态，**存储和引擎绑死**：多一个声部就多一整套
   地址发生器、流水寄存器和 24 块 BSRAM（48 深的阵列几乎填不满 18 Kbit 的块）。
   8 声部就要 192 块，占器件 56%。
2. 它的 7 个乘积靠**一个乘法器轮转**，`>>> SH_x` 的移位量由运行时的 `k` 选出来 ⇒
   桶形移位器留在关键路径上，所以 11 拍/模态、74.8 MHz 上不去。
3. 共用引擎把"每声部一套"变成"每声部一行地址"，7 个乘法器由 8 个声部分摊；
   存储按**模态总量**线性增长，而不是"声部数 × 每声部固定开销"。

## 4. 推到 16 / 32 声部

每声部每帧 = `N + 8` 拍（五级流水排空）+ 约 4 拍作业切换：

| | 吉他（20 模态/声部） | 钢琴（80 模态/声部） |
|---|---|---|
| 每声部每帧拍数 | 20 + 8 + 4 = **32** | 80 + 8 + 4 = **92** |
| 16 声部每采样拍数 | **512**（预算 25%） | **1472**（预算 **71%**） |
| 32 声部每采样拍数 | 1024（49%） | 2944（**141%**，必须 2 个引擎） |

> 钢琴一个"声部"是两根弦 × 40 模态 = 80 模态。16 声部时一个引擎就够（71%），
> 但只剩 29% 余量给腔体滤波，建议 2 个引擎（各 36%）；32 声部则必须 2 个。
> 吉他 20 模态很轻，16 声部只占 25%。

存储见第 2 节：钢琴 16 槽 83 块、吉他 16 槽 32 块；都要 32 槽时 ≈167 / 64 块。

`modal_bank_ram` 走同一条路会撞墙（存储和引擎绑死）：

- 按**算力**配：钢琴每声部 442 拍（11×40+2），16 声部 = 7072 拍/采样 ÷ 2083 ⇒ 4 个实例；
  但 4 个实例只放得下 4 个声部的系数/状态，剩下 12 个没地方住。
- 按**声部**配：16 个实例 ⇒ 逻辑 ≈ 26k（装得下），BSRAM ≈ 24 × 16 = **384 块 > 340**，超器件。
- 它没法把多个声部的模态"摊进同一个 bank"—— 那正是新架构做的事。

## 5. 口径与前提

- **BSRAM 块**：GW5AST 的 BSRAM 是 18 Kbit/块；本设计实测 8 槽 × 48 模态 + x/y = 23,040 B
  用了 28 块 ⇒ 823 B/块（理想 18,432 bit = 2,304 B/块，实际受位宽/深度取整影响约 2.8×）。
  第 2 节的块数是按 823 B/块折算的。
- **拍数**：`N + 8`（一帧，五级流水）+ 约 4 拍作业切换（实测：2 声部 × (4+8) 期望 24、实得 32）。
- **Fmax**：`syn/synth_pnr_one.tcl` + `constr/fmax.sdc`（10 ns）。括号里的"≈105 MHz"
  是 slack 换算（1000/(10−0.458)）——它说明 10 ns 约束**已经收敛**，不是精确的极限频率。
- 两种方案的 `x/y` 缓冲深度不同（`top_ram` 每采样一个作业 X_DEPTH=2；新架构块处理 X_DEPTH=64），
  这部分只影响几十块 BSRAM，已单列。
