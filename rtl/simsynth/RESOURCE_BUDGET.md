# 存储与资源核算（32 声部：吉他 / 钢琴）

> 口径：当前 RTL（逐字段 Q + 32 位尾数，`modal_step_pkg`）。
> 器件 **GW5AST-LV138FPG676AES**：138240 逻辑、139140 FF、340 BSRAM（18 Kbit/块，共 6.12 Mbit）、
> 298 DSP；48 kHz / 100 MHz ⇒ 每采样 **2083 拍**。

## 1. 一个模态要存什么

| 内容 | 位宽 | 位 | 字节 |
|---|---|---|---|
| `a11` / `a12` / `a21` / `a22` | 7 × 32 = 224 | 224 | 28 |
| `gq` / `gv` / `wo` | （含在上面 7 个字段里） | | |
| 状态 `q` | 32 | 32 | 4 |
| 状态 `q'` | 32 | 32 | 4 |
| **合计 / 模态** | | **288** | **36** |

- **没有额外元数据**：移位量是逐字段的编译期常量（`SH_A11…SH_WO`），不在记录里；
  旧格式（24 位尾数 + 每条目 6 位移位）每模态要 7×30 + 64 = 274 位，且精度差 78 倍。
- 状态按模态归一化（`sq = 2^QF/peak_q`），所以 `q/q'` 恒为 32 位定点，不需要浮点指数。

## 2. 两种乐器的总量

| | 吉他 | 钢琴 |
|---|---|---|
| 声部数 | 32 | 32 |
| 每声部弦数 | 1 | 2 |
| 每弦模态数 | 20 | 40 |
| 弦总数 | 32 | 64 |
| **模态总数** | **640** | **2560** |
| **系数 + 状态** | 640 × 36 B = **22.5 KiB**（180 Kibit） | 2560 × 36 B = **90 KiB**（720 Kibit） |
| 含 A/B 双份（ping-pong） | 45 KiB（360 Kibit） | 180 KiB（1.44 Mibit） |
| 折成 BSRAM（按实测打包效率 ≈ 6.7 Kbit/块） | **28 块** / 含 A/B **56 块** | **111 块** / 含 A/B **222 块** |

### 每声部的激励/结果缓冲（可选，按块处理深度算）

| 缓冲 | 每采样 | 深 64 时每声部 | 32 声部 / 含 A/B |
|---|---|---|---|
| `x`（激励） | 32 位 | 256 B | 8 KiB / 16 KiB |
| `y`（本声部 Σ wo·q） | 64 位 | 512 B | 16 KiB / 32 KiB |
| 小计 | 96 位 | 768 B | 24 KiB / 48 KiB（30 / 59 块）|

含这两块缓冲的总量：

| | 不含 A/B | 含 A/B |
|---|---|---|
| 吉他 | 46.5 KiB ≈ **58 块 BSRAM**（17%） | 69 KiB ≈ **115 块**（34%） |
| 钢琴 | 114 KiB ≈ **141 块**（41%） | 204 KiB ≈ **281 块**（83%） |

> 结论：**钢琴 32 声部（2560 模态）本身装得下，但 A/B 双份是"能不能装下"的分水岭**。
> A/B 只在"运行时重装声部系数"时才需要；32 个琴键固定，装载可以放在开机/换音色时做，
> 那时可以只保留一份（141 块，41%）。吉他则无论哪种配置都很宽松。

## 3. 8 声部：两种架构的实测对比

同一个器件、同一套 `syn + pnr` 流程、100 MHz 约束、`N_MODES = 48`、`DEBUG_PORT = 0`、
**两边都已修掉 `coeff_t` 结构体阵列的 FF 回退**（否则对比的是"谁的 bug 更贵"）。

| 指标 | `modal_bank_ram` × 8 实例 | **7 乘法器共用引擎 × 1** |
|---|---|---|
| 声部组织 | 每声部一个 bank（存储与引擎绑定），8 个并行 | 1 个引擎时分 8 个声部，存储在顶层 |
| Logic | 13104 | **1823**（7.2× 少） |
| Register | 6129 | **816**（7.5× 少） |
| BSRAM | 192 / 340（56%） | **48 / 340**（14%，4× 少） |
| DSP | 32（16 × MULT27X36） | **28**（14 × MULT27X36） |
| 每采样拍数（8 声部 × 48 模态） | 530（8 个并行，各自 11N+2） | **480**（8 × (56+4)） |
| **PnR Fmax（100 MHz 约束）** | **74.8 MHz**（slack −3.374 ns，未收敛） | **104 MHz**（100 MHz 下 slack +0.097 ns） |
| 每声部摊薄：Logic / Reg / BSRAM | 1638 / 766 / 24 | **228 / 102 / 6** |
| 关键路径 | 乘 → 64 位舍入 → **6 级桶形移位** → 累加（13.4 ns） | `bank_r` → 状态 2 选 1 → 乘法器输入（9.6 ns） |

**为什么差距这么大**

1. `modal_bank_ram` 一个 bank 只有 48 个模态，**存储和引擎绑死**：多一个声部就多一整套
   地址发生器、流水寄存器和 24 块 BSRAM（48 深的阵列几乎填不满 18 Kbit 的块，
   打包效率只有个位数）。8 声部就要 192 块，占器件的 56%。
2. 它的 7 个乘积靠**一个乘法器轮转**，`>>> SH_x` 的移位量由运行时的 `k` 选出来 ⇒
   桶形移位器留在关键路径上，所以 11 拍/模态、74.8 MHz 上不去。
3. 共用引擎把"每声部一套"变成"每声部一行地址"，7 个乘法器由 8 个声部分摊，
   逻辑和存储都按**模态总量**而不是"声部数 × 每声部固定开销"增长。

## 4. 推到 32 声部会怎样

| | 吉他（640 模态） | 钢琴（2560 模态） |
|---|---|---|
| 每声部拍数（N+8+切换 4） | 20+12 = 32 | 40+12 = 52 |
| 32 声部每采样拍数 | 1024（预算 49%） | 1664（预算 **80%**） |
| 需要几个引擎 | **1 个**（还有一半余量给腔体滤波） | **2 个**（各 40%）或 1 个但没余量 |
| 存储 | 22.5 KiB（28 块） | 90 KiB（111 块） |
| 1 个引擎的资源 | 1823 逻辑 / 816 FF / 28 DSP / 48 块 BSRAM（8 声部配置） | 同左，但模态更深 ⇒ BSRAM 按第 2 节算 |

`modal_bank_ram` 走同一条路会撞墙，原因是**存储和引擎绑死**：

- 按**算力**配：钢琴每声部 442 拍（11×40+2），32 声部 = 14,144 拍/采样 ÷ 2083 ⇒ 需要
  **7 个实例**并行；但 7 个实例只放得下 7 个声部的系数/状态，剩下 25 个声部没地方住。
- 按**声部**配：32 个实例 ⇒ 逻辑 ≈ 52k（装得下），但 BSRAM ≈ 24 × 32 = **768 块 > 340**，
  直接超器件。
- 它的存储没法"把 32 个声部的模态摊进同一个 bank"——那正是新架构做的事：
  存储按模态总量线性增长（640 / 2560 个模态），引擎数只由算力决定。

## 5. 口径与前提

- **BSRAM 估算**：按本设计实测的打包效率（8 声部 × 48 模态 × 2 份 = 319,488 bit 用了 48 块
  ⇒ 6.7 Kbit/块）折算；理想装箱是 18 Kbit/块，实际受位宽/深度取整影响，通常 2–2.8 倍。
- **拍数**：`N + 8`（一帧）+ 4 拍声部切换（实测：2 声部 × (4+8) 期望 24 拍、实得 32 拍）。
- **Fmax**：`synth_pnr_one.tcl` + `constr/fmax.sdc`（10 ns）；括号里的"104 MHz"来自
  换成 `fmax200.sdc`（5 ns）重跑后的最差路径 9.58 ns。
- 两者的 `x/y` 缓冲深度不同（`top_ram` 是每采样一个作业，X_DEPTH=2；新架构是块处理，
  X_DEPTH=64），这部分只影响几十块 BSRAM，已单列，不计入核心存储对比。
