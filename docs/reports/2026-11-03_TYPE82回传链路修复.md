# TYPE82 录制回传链路检查与修复（2026-11-03）

## 输入证据

用户17:11诊断：[原始JSON](evidence/2026-11-03_171105_有线录制诊断.json)。有线v1/115200，START/STOP均回复00、rxErrors=0，但performanceFrames=0，约2秒后missing_start_frame。该现象不是“有音符丢失”，而是起点也没有返回；背景见[实板联测记录](2026-11-03_实板功能与上位机录制联测.md)。

## 检查结论

生产链路为：performance_capture事件FIFO → comm_top → 有线transport_link → performance_frame_tx → UART TX。

在comm_top和transport_link两层中，perf_valid、perf_seq、perf_payload均使用带默认值的input logic声明，分别默认0、0和全零。在当前Gowin V1.9.12.04下，这种动态端口接法存在与之前backend_source_valid同类的综合失真。9188同批网表中performance_frame_tx的数据输入已常量化，事件描述符FIFO的ready握手仍存在。

于是采集侧可能把起点/结束描述符当作已接受并弹出，START/STOP依照现有规则回复成功；真正发送编码器却没有启动，UART只返回配置ACK。这个机制能解释本次JSON中ACK全部成功而TYPE82一个字节都没有的组合现象。

## 生产模块最小复现

新增的record_stream_probe实例化真实comm_top及其全部真实协议/编码器/UART模块，只用合成描述符生产者代替压力垫采集端；有效信号使用组合连接，与板级接法一致。测试从UART线独立解码，不读取内部发送计数冒充线端结果。
