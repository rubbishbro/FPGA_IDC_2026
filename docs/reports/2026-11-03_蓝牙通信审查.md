# 2026-11-03 蓝牙 / 上位机 / 本机通信审查

> 摘要自 [蓝牙 / 上位机 / 本机通信审查与仿真报告](../archive/2026-11/2026-11-03_bt_host_comm_review.md)。原文含逐条源码/测试证据；本篇保留 P0/P1 与当前动作。
>
> 本报告只做源码审查和 RTL 仿真；没有连接实体 HC-05、没有重新综合/布线/烧录。引脚结论必须用实物通断/示波器复核。

## 结论摘要

1. **RTL 的 v1 蓝牙链路本身在 9600、50MHz 下工作**。`tb_integration_bt_recovery_business` 用生产 `instrument_board_top`、真实 9600 位时间和独立主机 CRC/SLIP 模型通过 46 项检查，包括蓝牙帧错误隔离、32 位空闲恢复、无陈旧回复、蓝牙/有线隔离。
2. **“蓝牙通信失败”更像链路配置/接线问题，而不是协议状态机损坏**。主机 v1 原被界面强制为 115200，而板端蓝牙 UART 是 9600；界面没有 9600 选项。仿真复现：9600 主机能进配置，115200 主机一个有效帧都进不来，错误计数仍为 0（静默失败）。该 UI 锁定已先修（见第 6 节），RTL/CST 未改。
3. **界面仍把 v2 标成“蓝牙 UART”，但生产 RTL 已没有 v2 codec/session**。用户按界面提示选 v2 连蓝牙必然握手失败；选 v1 又会被强制 115200——当时没有任何一条可用蓝牙路径。
4. **CST 把蓝牙 RX/TX 改到了 T23/R23，而原理图上这两个球是 SDRAM_D13/D12（J23 SDRAM 连接器）**；上一版 R16/R17 和 STATE T24 都在 PMOD0 排针 J22 上。若 HC-05 仍插在 PMOD0，这次改脚会让 RX/TX 完全悬空；若模块确实接在 J23，则 STATE 又在另一个排针上，且要确认 SDRAM 模块未安装/不会总线争用。**当前最高风险硬件项。**

## 测试现状

- 大型 “independent” 协议 TB 当前 94 项检查、**10 项失败**；多项是 TB 自身写错/状态污染，不是 RTL 问题。不能作为“已验收”依据。
- 默认 `run_comm.py` 只跑 8 个单元 TB，不跑蓝牙集成/主机 UI；`run_board.py` 的蓝牙用 1.5625 Mbaud 加速，且 DUT 与解码器共用同一参数，无法发现生产默认值错误。
- 新增 BT/keymap 集成 TB 仍是未跟踪文件，没有进入默认回归；`run_record_uart.py` 在本机因缺少 `-MAKEFLAGS` 编译失败。
- 网页原 77 项测试里约 45 项是 v2 死路径；v1 串口测试用 2 Mbaud/115200，从未测过 9600；原测试也没有覆盖 `app.mjs` 的波特率强制逻辑（本次已补 2 项）。
- 板端当前生产默认：蓝牙 9600、有线 115200、v1 帧；见 [上板测试](../上板测试.md)。

## 建议动作

1. **先核硬件**：确认 HC-05 到底插在 PMOD0 还是 J23；用通断/示波器确认 T23/R23 是否真的接到模块 RX/TX，以及 STATE 的落点。若仍在 PMOD0，回退 R16/R17/T24 或改线。
2. **统一 UI**：v1 蓝牙只提供 9600，不再暴露 v2；v2 选项删除或标注“仅开发/不可用”。UI 锁定修复后补 9600 端到端测试。
3. **测试门禁**：把 BT/keymap 集成 TB 纳入默认回归；修 `run_record_uart` 编译；把 94 项大 TB 的 10 项失败逐条标注“TB 问题/RTL 问题”，不要用总数当验收。
4. **文档**：通信协议/上板测试/status 的蓝牙结论保持一致（板端 9600，UI 不能再锁 115200）。
