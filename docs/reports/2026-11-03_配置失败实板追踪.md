# 配置失败实板追踪（2026-11-03）

用户补充：音色、混响、音组、演奏来源均可进入并高亮，确认后左下角显示“失败”；piano1仍正常发声。因此首次选择范围缓存初始化缺陷不是这组提交失败的充分解释。

## 真实UART证据

通过现有libftd2xx访问USB Debugger B，序列号2025071717B，115200/8N1；A通道保持供JTAG使用。不依赖缺失的tty设备节点。使用当前SLIP/CRC协议。

- NONE请求SEQ A7/A8：回复06。A8首回复约50.8ms。
- 同一067C原位流重载后NONE请求SEQ AA仍回复06，约50.9ms。
- HALL/BATHROOM/NONE（SEQ B2/B3/B4）全部06，约41–52ms。
- CHAMBER=3（B6）回复06；非法值4（B7）回复03，约10.4ms；NONE（B8）再次06，约51.3ms。这证明当前边界参数校验能区分合法和非法值，CHAMBER也已识别。
- 诊断录制开始/停止（B0/B1）均返回00。该入口绕过config_dispatch标量提交，源码中准入依赖audio_valid && !audio_fault && source==0 && instrument_channel非0。故不能将故障直接解释为整个音频后端未启动。
- 最近一次NONE失败后再次录制开始/停止（B9/BA）的原始回复见eligibility_after_failed_config.json。
- 所有已取得回复的CRC逐帧校验通过。

结果06本身不能区分桥接拒绝、后端CFG_FAILED、config_dispatch对tag/id/applied_value/audio快照的校验失败。结合正常发声、录制准入成功、合法值比非法值多出约30–40ms，优先检查config_dispatch BACKEND_WAIT/BACKEND_CHECK中的backend_q、audio_q、audio_valid_q与audio_reply_ok，及对应后端完成事务。该时间差只是定位线索，不是内部状态的直接回读。

另做一次默认piano1低音组16键（21..36）的直接键位入口测试（B5），一秒观察期内无回复；该结果不能宣称入口成功或失败，可能涉及放键等待或其他阻塞，需内部状态确认。之后重新加载同一原位流撤销诊断状态。
