# Web上位机与RTL对接逻辑及资源分工（2026-11-03）

用户明确后续优先让Web承担适配，释放FPGA资源。本报告区分当前实现和可选后续方案；没有在本轮擅自修改协议或裁减RTL保护。

## 当前链路

```text
网页SerialLink（v1帧编码/重试）
  → USB-UART 115200 8N1
  → RTL UART / SLIP / CRC / 配置分析器
  → 板级桥接：校验、原子提交或录制启停
  ← TYPE80：原命令+结果码

PAD实际提交快照
  → RTL performance_capture：边沿检测、采样tick、事件FIFO
  → transport_link：回复优先仲裁，完整TYPE82帧不能被插断
  → UART回传
  → Web FrameReader / PerformanceRecorder
  → 音符轨道 / 钢琴卷帘 / 工程保存 / MIDI导出
```

### 连接和播放

有线v1为115200，蓝牙v1为9600；本固件没有v2心跳/会话层。SerialLink维护发送队列和诊断，播放消息封装为TYPE01 MIDI。网页负责播放调度、通道和已加载音高的预检查，板端负责接收、来源归属和音频执行。网页的“板端已加载配置”目前是手动核对清单，修改该清单不等于改动板卡音色/音组。

### 配置命令

Web的configure一次只允许一条在途配置；新请求使用新SEQ，500ms无回复时以相同SEQ和内容重试，最多3次。板端识别重复请求并重放结果，避免重复执行。TYPE80须CRC正确且SEQ、命令匹配才结束等待。回复00表示对应业务完成，失败不可由网页改写成成功。

当前v1业务主要为混响CMD02、整套16键绑定CMD20、录制START12/STOP13；没有远程音色/通道/音组的通用配置接口。网页v2工具不能作为当前固件能力。

### 录制

1. Web生成非零32位录制ID，发送CMD12+小端ID。
2. RTL确认音频就绪、PAD来源和有效通道，在实际采样边界启动。
3. RTL发送TYPE82起点；Web必须同时等到START的00回复和起点，才显示REC。起点缺失2秒后尝试STOP，并标记不完整。
4. PAD变化由RTL按实际提交快照产生按下/松开事件，携带ID、ordinal、slot、channel、采样tick、音高和起音力度。
5. Web按ID隔离录制、按ordinal检查丢帧/重复，按slot配对NoteOn/Off。时间用tick×256/12500000换算秒，再结合tempoMap换算节拍；不使用USB到包时间推算演奏时刻。
6. 停止使用相同ID；RTL在采样边界停止并排空结束描述符。Web收到正常END后封口音符、生成轨道；超时/缺帧则保留不完整标记。

回传的是音符事件，不是PCM。源码位置：web/midi-editor/src/{serial,protocol,recording-ui,performance-recorder,midi-file}.mjs；RTL为performance_capture、transport_link、performance_frame_tx、comm_top和instrument_system。

## 优先放在Web的工作

| 工作 | 分配建议 | 原因 |
|---|---|---|
| 曲谱编辑、长时间录制存储、轨道合并 | Web | 浏览器内存充足，无需占FPGA RAM |
| tick→秒→节拍、tempo变化、量化、音符配对、MIDI导出 | Web，当前已主要实现 | 与设备实时合成解耦 |
| 去重、序号缺口诊断、不完整轨道封口、日志 | Web，当前已有 | 便于更新和观测 |
| 键位表生成、音域/资源清单预检查 | Web | 提前拦截错误，减轻设备复杂业务；板端仍保留简明合法性检查 |
| 兼容不同协议/固件的数据布局 | Web适配层 | 不为UI差异反复扩展RTL状态机；应按已知固件能力显式选择，不能猜测成功 |
| 自动重连、可视化诊断、用户引导 | Web | 不需要FPGA实现复杂会话UI |

## 板端保留的最小责任

实际PAD采集/已提交音符快照、采样时间戳、事件顺序、短时队列与有界溢出处理、UART帧完整性、同一请求去重/原子提交及断连安全。这些保护不能靠Web“适配”补回：板端没发出的事件和错误时间戳无法从主机接收时间可靠恢复。

## 后续资源优化候选（尚未实施）

- **缩小事件线上格式或批量封帧**：会话ID/采样率等放在起点帧，后续发送紧凑事件，Web重建完整事件对象。可能减少payload寄存器/复用器和UART带宽。需明确新版本标识并保留Web旧格式适配，不能直接静默改变24字节ABI。
- **短FIFO，长录制留Web**：现有128×112位FIFO只缓冲突发事件，不存整段录制。是否减深度须测满16垫同时起落、USB/回复阻塞下的峰值积压；不能假设浏览器缓存能替代发送前的FIFO。
- **降低板端重复业务解码**：表头一次解码、逐项分拍已实施；复杂编辑/变换继续在Web做。板端保留小而确定的验证与提交逻辑。
- **暂不实现板端SMF文件、节拍网格、多轨合并、完整录音缓存或PCM上传**，优先使用现有事件流和Web处理。

这些是后续选择，不在本轮额外实现。优先级为：现有事件回传实板闭环→依据资源报告选一个紧凑协议方案→Web双格式适配→RTL裁减→门级/带宽/时序验收。
