# 上位机可行性分析：WebGL MIDI 编辑器 + FPGA 实时合成器

> 评估日期 2026-10-22，**二次修订：新引擎核心 + 完整后级已上架**（POST_EN=1，回归 16 项，P&R Fmax 100.166 MHz）。
> **讨论稿：方案尚未定。** 未修改 RTL，未写任何上位机代码。
> 结论中的带宽、周期、资源数字来自仓库现有报告与源码；链路吞吐和延迟**必须实测**，本文给出实测方法和判据。
> 相关：[ENGINE_INTERNAL](ENGINE_INTERNAL.md)、[TIMING_RAM_ANALYSIS](TIMING_RAM_ANALYSIS.md)、[rtl/README](../rtl/README.md)、[产品需求与竞品调研](产品需求与竞品调研.md)。
> Step 1 结构稿已归档：[新架构总览_step1](../history/docs/legacy/新架构总览_step1.md)。

## 0. 结论速览

**一句话：编辑器可以做，多轨可以做，弯音可以做；数据面走 UART，音频回传可以但必须分级。**

| 需求 | 可行性 | 前提 / 卡点 | 粗估 |
|---|---|---|---|
| WebGL 钢琴卷帘 + 多轨编排 | **高** | 无硬性卡点，纯前端 | 3–4 人周 |
| MIDI 导入/导出、循环、量化、撤销 | **高** | 无 | 1–2 人周 |
| 浏览器本地试听（不接硬件） | **高** | 要和板子一致就得用同一套定点模型（WASM） | 1–2 人周 |
| 音符/力度/弯音**编辑** | **高** | 界面层，无卡点 | 1 人周 |
| 弯音**在板端生效** | **中** | 需要新的系数生成通路，且 Fmax 余量只剩 0.17% | 2–3 人周 |
| 上位机 → 板子 事件链路 | **可行** | 需新写 UART + 协议 + `host_link` RTL | 2 人周 |
| 板子 → 上位机 **音频回传** | **可行（有条件）** | 单声道 781 kbps / 2 Mbaud 占 49%；立体声 1.56 Mbps / 3 Mbaud 占 65%，**需实测** | 1–2 人周 |
| 多轨**同时多音色**发声 | **有条件** | ABC 内可以；含 E2 不行；上限 16 voice | — |
| 32 复音 | **不建议承诺** | 新架构 16 槽，周期预算已紧 | — |

**推荐首版范围：** 一个 Chromium 里跑的本地优先编辑器（WebGL 卷帘 + 多轨 + MIDI 导入 + WASM 试听），一根 USB-C 线同时完成烧录与事件/音频双向传输，音频从板子的 3.5 mm/喇叭出，回传只做「监控级」录音。**不要**把「32 复音」「跨引擎多音色」写进首版承诺。

## 1. 需求拆成三层，工作量差别极大

用户原话里的六件事，落在完全不同的层：

```text
第 1 层  UI/编排（纯浏览器）      ：本地编排、多音轨、弯音编辑、WebGL 渲染
第 2 层  链路（浏览器↔板子）      ：连接、事件下发、音频回传、烧录
第 3 层  DSP（板端）              ：弯音生效、多音色、复音、后级
```

三层里**第 1 层几乎无风险**（成熟 Web 技术），**第 3 层是真正的工程量**，而「回传」这件事同时横跨第 2 层和第 3 层，需要拆开回答。

竞品（musiccreator.ai / signal）只做第 1 层：它们是「网页里的 MIDI 编辑器 + 浏览器内合成」，声音由 SoundFont 在浏览器里渲染。我们要多做的是把第 1 层和第 3 层用第 2 层接起来——**这部分没有现成产品可抄，是本项目真正的差异化，也是主要风险。**

## 2. 现有工程的「接口现实」

好消息比预期多。设备侧已经有的事件接口，几乎就是为上位机准备好的。

### 2.1 已经现成的

[router_system_top.sv](../rtl/core/router_system_top.sv) 的端口：

```text
load_valid / load_ready / load_class / load_voice / load_inst / load_note
load_vel / load_dyn / load_note_id  →  load_done / done_voice / loaded_n_modes / load_error
off_valid / off_voice                →  note off

rcfg_valid / rcfg_instrument[3:0] / rcfg_voice / rcfg_note / rcfg_velocity
fmap[16*8] / fmap_valid              →  router_frontend → excitation_convert → x
start / sample_ready / busy / done / out_valid / mix_sum
```

这组端口就是「音符事件」的完整语义（含力度、动态层、note id、拒绝契约），**上位机可以一对一映射**，不需要发明新的演奏模型。

压力矩阵走的是另一条 `rcfg/fmap → router_frontend → excitation_convert` 路径，但目前它只是 **A 路径 MVP**：把 `x` 注入 0 号槽（`a_x_eff[0] = r_x`），并不自己做声部记账。所以上位机和本机共用的是同一套 engine/RAM，**分槽仍然要在 `router_voice_alloc` 这一层显式约定**。

更关键的是 [shared_modal_ram.sv](../rtl/core/shared_modal_ram.sv)：每个 voice 的 9×32 记录里存的是 **G / a1 / a2 系数本体**，由 [router_loader.sv](../rtl/core/router_loader.sv)（`index_loader20` / `index_loader64`）在 note-on 时从 flash 装进该 voice 的槽位。

**推论：每轨不同音色在 ABC 内是天然支持的**——voice 0 装 guitar、voice 1 装 piano，只要都走 `abc_engine`（`abc_lane_core ×4`）。engine_mux 选的是**核**，不是**音色**。

后级也上架了：[post_chain.sv](../rtl/core/post_chain.sv) = `envelope_mul → body_biquad → comb_reverb → dry_wet_mix → final_adder`，`POST_EN=1` 是正式配置。也就是说「板子真正听到的」现在确实是一条完整链，回传和本地试听有了明确的对照点。

### 2.2 真正的限制

| 限制 | 现状 | 对多轨的影响 |
|---|---|---|
| `NUM_SLOTS = 16` | 新共享架构 16 voice | 16 轨不是 16×N 复音，是全局 16 个发声槽 |
| `load_inst` 只有 **2 bit** | load 事件路径 2 bit；压力路径 `rcfg_instrument` 已经是 4 bit | 产品有 10+ 音色，**协议按 8 bit 设计，RTL 两边都要放宽** |
| E2 与 ABC **互斥** | `engine_mux` 二选一 | 含 E2 音色的轨不能和 ABC 轨同时响 |
| 后级是**全局单套** | 已实现（env→body→reverb→dry/wet→final），但只有一套 | 不能每轨独立 EQ/混响 |
| 后级参数**不可写** | `post_env_gain/gd/gw` 在 `shared_engines_system_top` 里固定为 `0x8000/0x4000/0x4000` | 上位机要调混响/干湿，得先把这三个端口引到 top 或加参数寄存器 |
| 没有 UART/USB 输入 | 全仓库无 `host_link` | 第 2 层要从零写 |
| 没有声部分配器 | `router_voice_alloc` 只按**显式 voice** 更新 active/gate | 上位机分配 voice 仍然可行，RTL 不用写分配器 |

### 2.3 两个容易踩的时序事实

1. **板端现有输出链路的采样率不是 48000，是 48828.125 Hz**（12.5 MHz / 256，BCLK 3.125 MHz，16 bit 单声道左右复制）。
   上位机如果要「和板子听起来一样」，本地模型必须用 48828.125 Hz，否则整体高 **+29.6 音分**（约 1/3 个半音，能被听出来）。[工程汇报](../history/docs/工程汇报.md) 已把这个列为已知风险。
2. **每样本 2048 拍**（100 MHz / 48828.125 Hz = 2048.0，整数，设计是自洽的）。
   当前 [abc_lane_core.sv](../rtl/core/abc_lane_core.sv) 每个 mode 走 9 拍、4 lane 并行：

```text
每 voice 周期 ≈ ceil(n_modes/4) × 9（不含 1–2 拍收尾）
  n_modes=16 → 4 × 9 = 36 拍   → 16 voice = 576 拍  = 28% 预算
  n_modes=32 → 8 × 9 = 72 拍   → 16 voice = 1152 拍 = 56% 预算
  n_modes=48 → 12 × 9 = 108 拍 → 16 voice = 1728 拍 = 84% 预算
```

也就是说：**16 voice 满载 48 模态时只剩约 320 拍**给包络、biquad、混响、弯音系数更新——而后级现在已经上架（`POST_EN=1`），这部分余量已经被吃掉一部分。结论没变：弯音系数更新必须走「后台低速 + 块内插值」，不能占样本级预算；再往上加后级或多音色，模态数或复音数必须砍。

时序余量也别忘了：[TIMING_RAM_ANALYSIS](TIMING_RAM_ANALYSIS.md) 的最新 P&R 是 **Fmax 100.166 MHz，slack +0.017 ns**（LUT 10,050 / FF 6,054 / BSRAM 113 / DSP 56）。后级上架后余量从 2.7% 掉到 **0.17%**，而且现有 SDC 没写 clock uncertainty / jitter，真实板级只会更差——任何动 lane core 或后级的方案都要重跑 P&R。

后级链现在是默认路径（`POST_EN=1`），它的状态机在 `pstate 2` 有一个 **1024 次 handshake 循环**（`post_cnt >= 1023` 才拉 `done`）。`done` / `sample_ready` 都被它限定，所以**每个输出样本的拍数不再只由引擎决定**；如果这是 `tb_shared_engines_post` 用的尾音诊断，正式出声前要确认它该不该留在默认路径。

## 3. 有线链路：UART

### 3.1 板上的串口从哪来

从原理图 `TANG_MEGA-138K_Pro-Dock-4071f`：

| 接口 | 器件 | 连到 FPGA 的信号 | 说明 |
|---|---|---|---|
| USB-C 调试口 | **BL616C**（QFN40） | `DBG_UART.RX=N16`、`DBG_UART.TX=P15` | 一颗 MCU 做 USB↔UART 桥，同时承担烧录 |
| 音频输出 | **PT8211-S**（16 bit 立体声 DAC）→ 耳机/喇叭功放 | `I2S_BCLK=E22`、`I2S_LRCK=F24`、`I2S_DIN=G24` | 板端真实输出精度就是 16 bit |

> 引脚来自原理图网表，**必须以官方 `.cst` 复核后再写约束**，不得直接照抄本文。

**桥的形态（2026-10-22 调研）：** 板载调试器是 **BL616**（Sipeed 固件 `bl616_fpga_partner_138kproDock.bin`）。从 Sipeed FAQ 的「两个 USB Converter + 一个 COM、converter B 可加载 VCP、重装 FTDI 驱动」来看，固件在 USB 上**模拟 FT2232H**，VID:PID 大概率是 `0403:6014`。对上位机来说，它就是一个**标准串口**：

```text
串口：VCP，Linux 是 /dev/ttyUSB*，Windows 是 COMx
烧录：同一个 USB-C，Gowin Programmer 或 openFPGALoader
```

### 3.2 上限与预算

| 项 | 值 | 依据 |
|---|---|---|
| BL616 UART 上限 | **10 Mbps**（160 MHz 时钟 / 16 bit 分频） | BL616 参考手册 §10 |
| USB | 2.0 HS 480 Mbps | BL616 数据手册 |
| 推荐速率 | **2.5 Mbaud**（160M/64）或 **4 Mbaud**（160M/40），都是整数分频 | — |
| 8N1 净荷 | 2 Mbaud = 200 kB/s；4 Mbaud = 400 kB/s | — |
| 实际需要 | 单声道 16 bit/48.828k = 97.7 kB/s；立体声 = 195.3 kB/s | — |
| 占用率 | 单声道 @2M = 49%；立体声 @4M = 53% | — |

**结论：够，而且余量充足。** 硬件上限比需求高一个数量级，真正的风险在固件是否按设定波特率跑、驱动缓冲和延迟，不在 UART 本身。

### 3.3 主机侧

浏览器用 **Web Serial** 直接打开这个 VCP：不需要本地桥，Linux/macOS 免驱，Windows 走 FTDI VCP 驱动。限制是只有 Chromium 系支持、页面必须 `localhost` 或 https、首次要用户授权。

> Linux 上打不开 `/dev/ttyUSB*` 时，先看 `dialout` 组；再检查 Gowin Programmer 装的 udev 规则——它会对 `0403:6014` 执行 `unbind ftdi_sio`，装过之后串口可能直接消失（见 §11 E1）。

### 3.4 四个必须处理的工程问题

1. **没有硬件流控**：原理图只接了 TX/RX，BL616 的 RTS/CTS 没引出。溢出只能靠**序号 + 丢帧 + 足够大的 FIFO**，不能指望反压。
2. **FTDI latency timer 默认 16 ms**：会固定加到上行音频的延迟上，Windows 设备管理器 / Linux sysfs 里调到 1 ms。
3. **串口和烧录互斥**：官方 FAQ 说串口被占用时烧录不可用，烧录前要关串口或重新插拔。
4. **波特率必须实测**：FAQ 记录过「实际波特率是设定值的 4 倍」的固件 bug。先确认调试器固件是 `2025030317` 或更新，再按 §11 E1/E2 量一遍。

## 4. 带宽与延迟预算

采样率按 **48828.125 Hz**、位深 **16 bit**（PT8211 的上限）算。

| 流 | 计算 | 速率 | 3 Mbaud（净荷 2.4 Mbps）占用 |
|---|---|---|---|
| MIDI 事件 | 512 事件/s × 13 B | ~53 kbps | 2% |
| 遥测（电平/声部/饱和计数） | 50 Hz × 32 B | 13 kbps | <1% |
| 音频 单声道 16 bit | 48828 × 16 | 781 kbps | 33% |
| **音频 立体声 16 bit** | 48828 × 32 | **1.5625 Mbps** | **65%** |
| 音频 24k 单声道（降级备份） | 24414 × 16 | 390 kbps | 16% |

结论：**3 Mbaud 下单声道很宽裕，立体声 65% 占用属于「能用但没有余量做重传」**。所以音频流设计成「**可丢、不重传、带序号**」，丢帧由上位机补静音并计数，而不是靠重传——重传会引入不可控延迟。

延迟分解（上位机按键 → 板子出声）：

```text
浏览器事件循环 + Web Serial 写入   ~0.5–1 ms（受 requestAnimationFrame/任务调度影响）
USB 主机到桥（HS 批量）            ~1 ms；FTDI 驱动 latency timer 默认 16 ms，要手动调到 1 ms
UART 13 B @3 Mbaud                 ~43 µs
设备侧排队 + 下一个样本边界          ~21 µs
系数装载（48 模态）                待测，估计 3–10 µs
---------------------------------------------
合计                               ~2–4 ms，瓶颈在 USB
```

**能用于编辑/试听，不能用于承诺赛题的 ≤10 ms 演奏延迟**——那是本机压力矩阵这条路的指标，两码事，报告里必须分开写。

## 5. 协议草案

原则：**二进制、定长头、可变长体、SLIP 定界、CRC16 校验、带序号和版本**。不用裸 MIDI 字节流（浏览器拿不到系统 MIDI 口，见 §5.3），但**语义沿用 MIDI**，方便以后接虚拟 MIDI 口。

### 5.1 帧格式

```text
┌──────┬──────┬────────┬───────────┬────────┐
│ type │ len  │ seq16  │ payload   │ crc16  │
│  1B  │  1B  │  2B    │ 0..64 B   │  2B    │
└──────┴──────┴────────┴───────────┴────────┘
整帧（type..crc）做 SLIP 转义，前后各一个 0xC0 定界。
CRC16-CCITT（poly 0x1021, init 0xFFFF），覆盖 type..payload。
```

选 SLIP 而不是 COBS：解码器是 3 个状态的 FSM，RTL 里十几行就能写完；COBS 的零字节消除在 RTL 里反而更绕。

### 5.2 消息表

**主机 → 设备**

| type | 名称 | payload | 说明 |
|---|---|---|---|
| 0x01 | `NOTE_ON` | voice(1) cls(1) inst(1) note(1) vel(1) flags(1) [note_id(2)] | flags: bit0 dyn，bit1=1 时追加 note_id |
| 0x02 | `NOTE_OFF` | voice(1) | 按槽位关，不按音高关 |
| 0x03 | `BEND` | voice(1) bend_lo(1) bend_hi(1) | 14 bit 有符号，8192 = 0 |
| 0x04 | `BEND_RANGE` | voice(1) semitones(1) cents(1) | 默认 ±2 半音 |
| 0x05 | `PARAM` | id(2) value(4) | 主音量、混响 dry/wet、全局 EQ… |
| 0x06 | `PATCH_BEGIN` | addr(2) len(2) | 后续 DATA 写入系数区 |
| 0x07 | `PATCH_DATA` | bytes… | |
| 0x08 | `PATCH_END` | crc16(2) | 一次性提交，避免半套系数 |
| 0x09 | `ALL_NOTES_OFF` | — | 断连恢复、切轨、停止 |
| 0x0A | `VOICE_PARTITION` | host_first(1) host_count(1) | 本机与上位机分槽 |
| 0x0B | `AUDIO_CFG` | enable(1) decim(1) ch(1) fmt(1) | 回传开关与降采样 |
| 0x0C | `PING` | ts(4) | 测 RTT / 估时钟偏移 |
| 0x0D | `QUERY` | what(1) | 能力、状态、计数器 |

**设备 → 主机**

| type | 名称 | payload |
|---|---|---|
| 0x81 | `ACK/NACK` | seq(2) code(1) |
| 0x82 | `TELEM` | sample_cnt(4) active_mask(2) busy_pct(1) sat_cnt(1) flags(1) |
| 0x83 | `AUDIO` | sample_cnt(4) n(1) pcm16[n*ch] |
| 0x84 | `PONG` | host_ts(4) sample_cnt(4) |
| 0x85 | `CAPS` | proto_ver(1) voices(1) classes(1) insts(1) features(2) |
| 0x86 | `EVENT_ACK` | voice(1) status(1)；status=0 装载成功，1 拒绝（对应 `load_error`） |

### 5.3 为什么不是 Web MIDI

浏览器只有 **Web MIDI**，它只能访问操作系统里注册的 MIDI 设备。板子的 USB-C 是一个 USB↔串口桥，**不会**被系统识别成 MIDI 口。所以：

```text
想用 Web MIDI  → 必须做虚拟 MIDI 口（Windows loopMIDI / macOS IAC / Linux snd-virmidi）+ 本地桥
想少一个依赖    → 直接用 Web Serial 打开串口（Chromium 自带，无需驱动/安装）
```

**结论：用 Web Serial。** 外接 MIDI 键盘仍可用 Web MIDI 收（那是另一条链路），两者互不影响。

### 5.4 时序策略

- 默认「立即执行」：事件到达下一个样本边界生效，抖动 ~2 ms。
- 若实测抖动 >3 ms，再给 `NOTE_ON` 加一个 `delay_us(2B)` 字段，设备端用 sample counter 做简单调度（RTL 成本：一个比较器 + 一个小 FIFO）。
- **不做**重传、不做停等；音频流自带 `sample_cnt`，丢帧由上位机按序号补齐。

## 6. 设备侧 RTL：`host_link`

### 6.1 框图

```text
DBG_UART.RX ─► uart_rx ─► slip_dec ─► frame_parser ─► cmd_queue(32)
                                                          │
                                    ┌─────────────────────┼──────────────────┐
                                    ▼                     ▼                  ▼
                              note 事件(FIFO)        param 寄存器       patch 写入器
                                    │                     │                  │
                                    ▼                     ▼                  ▼
                        router_system_top.load/off   后级参数*       系数 RAM/影子区
                                    │
   sample_ready ─► 音频抽头(可选抽取) ─► packetizer ─► slip_enc ─► uart_tx ─► DBG_UART.TX
   status        ─► telem 打包 ─────────┘

* post_env_gain / gd / gw 目前在 shared_engines_system_top 里写死（0x8000/0x4000/0x4000），
  要由上位机调，得先把这三个 16-bit 端口引到 top 或加一个参数寄存器。
```

### 6.2 关键设计决定

**① 声部分配放在上位机，不写 RTL 分配器。**
设备已经有 `load_voice` / `off_voice` 显式槽位端口（本机压力键盘的 `rcfg/fmap` 前端目前只注入 0 号槽的 x，不占声部记账）。上位机知道每轨用了哪些槽，天然支持「每轨固定声部数」「抢占最老音符」「轨道静音」这些 DAW 语义，RTL 只要一个 FIFO + 转发。省下的正是最容易写错的一块。

**② 本机与上位机分槽。**
16 个槽不能被上位机占满，否则压力键盘没声音。协议里用 `VOICE_PARTITION` 约定，例如 `host=8..15`（8 槽给电脑）、`local=0..7`。切换模式（纯本机 / 纯上位机 / 混合）由 UI 控制。

**③ 事件与装载解耦。**
`load_done` 是异步的（要从 flash 读 48 个模态），上位机收到的 `EVENT_ACK` 只代表「已入队/已装载」，不代表已出声。UI 上不要用 ACK 做播放时钟。

**④ 音频抽头挂在混音之后、I2S 之前。**
这样回传的是「板子真正听到的东西」（含后级、混响），而不是某个中间量。抽头只读 `mix_sum`，不占 RAM 端口。

**⑤ 时钟域只有一个（100 MHz）。**
UART 3 Mbaud 在 100 MHz 下是 33.3 clk/bit，用分数分频累加器 + 8× 过采样就够，不需要第二个时钟域。

### 6.3 资源与周期

| 项 | 估计 | 依据 |
|---|---|---|
| LUT | +400 ~ +800 | UART + SLIP + 解析 + FIFO |
| FF | +300 ~ +600 | |
| BSRAM | +1 ~ +3（命令 FIFO + 音频 FIFO） | 340 总量，现用 47 |
| DSP | 0 | 纯控制路径 |
| 周期 | 不占样本预算（独立于 engine 的流水线） | 只有音频抽头的 1 拍/样本 |

风险不在资源，在**时序**：新增逻辑要放在独立区域，不碰 lane core；P&R 后 Fmax 必须仍 ≥100 MHz。

### 6.4 测试

- `tb_host_link`：喂字节流 → 检查 `load_valid/note/vel/voice` 与 `ACK`；错误 CRC 必须被丢弃且不产生事件。
- 回归：现有 16 项（`sim/run_core.sh`）全 PASS 后才能上板。
- 上板：先做 UART 回环（收什么发什么），再做「网页按键 → 板子响」。

## 7. 音频回传

### 7.1 三档，按代价排序

| 档 | 内容 | 带宽 | 需要什么 | 建议 |
|---|---|---|---|---|
| **L0 遥测** | 电平/频谱包络（每 20 ms 一个 RMS + 8 个频段） | <20 kbps | 只要 RTL 算 RMS（或上位机从音频流算） | 先做，UI 立刻有反馈 |
| **L1 监控音频** | 48.8k 单声道 / 24.4k 立体声（781 kbps），或 24.4k 单声道（390 kbps） | 390–781 kbps | UART + FIFO + 帧 | **首版就做这个** |
| **L2 全质量** | 48.8k 立体声 16 bit | 1.5625 Mbps | 同上，要求链路 ≥2.5 Mbaud 稳定 | 实测通过后再开 |
| **L3 更高规格** | 96k 或更多通道 | >3 Mbps | 需要换传输，不在本方案内 | 不做（24 bit 对 16 bit DAC 无意义） |

注意：板子的 DAC 只有 16 bit，**回传 24 bit 没有意义**（内部 `mix_sum` 是 64 bit，但输出链路是 16 bit）。

而且当前 I2S 是 **16 bit 单声道左右复制**，所以**单声道回传就够了**：781 kbps，2 Mbaud 只占 49%，3 Mbaud 占 33%。立体声只有以后加了声像才需要。

### 7.2 丢帧与时间戳

- 每帧带 `sample_cnt`（32 bit，从复位开始计），上位机按序号拼接，发现跳号就补静音并在 UI 标红。
- **不要用主机时间戳对齐音频**：主机的音频时钟和板子的 48828.125 Hz 会漂移，用设备计数器才准。
- 断连恢复：设备端音频 FIFO 满就丢**最新**帧（而不是最老），保证延迟不累积。

### 7.3 合规边界

赛题要求「所有输出音频由 FPGA 实时生成，严禁预录 PCM 播放」。回传是**观测**方向，不参与发声，合规。但报告里要写清楚：

- 上位机试听/导出 WAV = **模型渲染**，不是硬件实录；
- 只有带 `sample_cnt` 的回传流才叫「硬件实录」；
- 演奏发声链路必须仍然是「压力矩阵 → router → engine → I2S」，上位机不在这条路上。

## 8. 弯音与实时变调（最硬的 DSP 项）

### 8.1 为什么难

模态合成的每个模态是二阶递推：

```text
y[n] = G·x[n] − a1·y[n−1] − a2·y[n−2]
a1 = −2·r·cos(θ),  a2 = r²,  θ = 2π·f/fs
```

系数是**离线按音高算好**放进 flash 的。弯音 = `f → ρf`，而 `cos(ρθ) ≠ ρ·cos(θ)`，**不能靠缩放 a1 实现**，必须重新算 cos。

### 8.2 三种实现

| 方案 | 做法 | 成本 | 音质 | 风险 |
|---|---|---|---|---|
| **A 系数调制**（推荐） | 控制率 1–2 kHz 重算 `a1/a2`，块内线性插值 | 每 (voice,mode) 一次 cos + 2 乘；48×4×1.5k ≈ 288k 次/s，占 ~3% 周期 | 正确：所有模态按比例移，衰减不变 | 要动系数 RAM 的写入时序；Fmax 余量小 |
| **B 变速重采样** | 每 voice 输出做分数延迟重采样 | 每 voice 2 乘 + 1 小 FIFO | 频率对了，但衰减时间随音高变（±2 半音约 ±12%） | 要拿每 voice 的输出（引擎目前是混音后输出） |
| **C 半音查表** | 每半音一套系数，切换时交叉淡化 | 内存 ×N | 只能半音级，做不了连续弯音 | 表太大 |

**推荐 A**，理由：它同时解决 **+29.6 音分的采样率偏差**——这个偏差本质上就是「整体音高乘了一个常数」，和弯音是同一条通路。做完 A，顺手把音准拉回标准音。

### 8.3 稳定性论证（给评审看的一句话）

递推的稳定域是 `(a1, a2)` 平面上的**三角形**：

```text
a2 < 1,  a2 > a1 − 1,  a2 > −a1 − 1
```

三角形是**凸集**，所以两个稳定系数点之间的线性插值仍然稳定。这为「块内插值」提供了严格依据，不是经验做法。步长够小（1.5 kHz 更新、±2 半音）时也不会产生可闻的拉链噪声。

### 8.4 工程量与先后

```text
Step 1  单 voice、单模态：离线算 a1/a2 曲线，验证频率准确度（Python）
Step 2  RTL：cos LUT(1024) + 插值 + 每 voice 影子系数区（双缓冲，tick 边界切换）
Step 3  引擎读影子区；只在 tick 空档写，避免读到半套系数
Step 4  16 voice × 48 模态压测周期 + P&R
Step 5  E2 的弯音单独处理（2×2 状态空间，要矩阵指数，工作量约 2 倍）
```

**E2 先不做弯音**：`a11..a22` 是离散状态转移矩阵，随频率变化要重算 `exp(A/fs)`，不是一条 cos 能解决的。首版把 E2 标成「不支持弯音」，UI 上灰掉。

### 8.5 风险

- Fmax 只有 **100.166 MHz / +0.017 ns**（后级上架后余量 0.17%），系数生成器如果接到 lane 的读路径上，很可能把时序打穿。必须做成**旁路写 RAM**，不碰 lane 组合逻辑。
- 内存带宽：16 voice × 48 模态 × 2 系数 × 1.5 kHz ≈ 2.3 M 写/s，占 100 MHz 的 2.3%，可以忽略；但和引擎的读口仲裁要设计好。

## 9. 多轨：编辑层的「轨」和板端的「槽」是两回事

| 说法 | 含义 | 现状 |
|---|---|---|
| 上位机 16 轨 | 编辑概念，可以有 100 轨 | 纯 UI，无限制 |
| 板端 16 voice | 同时发声的模态组 | `NUM_SLOTS=16` |
| 4 类 engine | A/B/C/E2 计算路径 | `engine_mux` 同一时刻选一个核 |

可行组合：

| 组合 | 能否同时发声 | 说明 |
|---|---|---|
| guitar + piano + flute（都是 ABC） | ✅ | 每 voice 自带系数，共用 `abc_engine` |
| ABC + E2 音色 | ❌ | `engine_mux` 二选一，切过去要重载 |
| 17 个音同时按 | ❌ | 只有 16 槽 |
| 每轨独立混响 | ❌ | 后级已实现但全局单套，参数还写死 |
| 每轨独立音量/声像 | ⚠️ | 需要每 voice 增益，现在没有；可在混音后做总音量 |

**产品上的处理：** UI 允许 16 轨，但实时播放时把「当前可发声的轨」限制在 ABC 内，并在状态栏显示「本轨使用 E2，播放时会静音其他轨」。**不要**做一个看起来能 16 轨同时响、实际只有 16 个音的界面。

另外 `load_inst` 只有 2 bit——协议先按 8 bit 设计，RTL 侧扩宽是顺手的事，但**不要**等做到第 10 个音色才发现。

## 10. 上位机（WebGL）实现

### 10.1 技术栈

```text
构建      Vite + TypeScript
框架      React / Svelte（都行；状态简单，别上重框架）
渲染      钢琴卷帘用 WebGL2（PixiJS v8 或裸 WebGL2 + instancing）
          DOM 只放表单、对话框、菜单；不要把卷帘做成 DOM
状态      Zustand + Immer patches（撤销/重做直接复用 patch 栈）
存储      IndexedDB（工程自动保存）+ File System Access（另存 .json/.mid）
音频      AudioWorklet + WASM（定点模型，见 10.3）
通信      Web Serial（主）+ Web MIDI（外接键盘）
文件      @tonejs/midi 或自写 SMF 解析（格式简单，自写可少一个依赖）
```

### 10.2 WebGL 到底值不值

值，但只在三个地方值：

1. **卷帘规模**：16 轨 × 数千音符，DOM 方案在 2k 音符就开始卡；WebGL 一个 instanced draw call 画 10 万音符仍然 60 fps。
2. **频谱/波形**：回传音频的实时频谱、波形、李萨如图形，用 shader 画比 Canvas2D 省 CPU。
3. **模态可视化**（可选加分项）：每个音的模态频率/阻尼画成 3D 柱状或极坐标，正好展示「参数化合成」的特点。

不值得的地方：表单、菜单、对话框、旋钮——DOM + CSS 更快更好维护。**混合渲染，别为了 WebGL 而 WebGL。**

性能预算：10k 音符 / 16 轨 / 60 fps 对任何集显都不构成压力；真正要小心的是**每次滚动都重建 buffer**——用 uniform 偏移 + 视口裁剪，不要每帧重传顶点。

### 10.3 数字孪生（关键设计）

浏览器里的试听不要用 SoundFont（音色和板子完全不一样，会误导用户）。做法：

```text
同一套定点 C 模型
  ├─ 作为 RTL 的黄金参考（已有 Python 模型，改成 C 更接近硬件语义）
  ├─ 编译成 WASM 给 AudioWorklet（实时试听）
  └─ 在 Worker 里离线跑（导出 WAV，和板子逐样本对得上）
```

采样率必须是 **48828.125 Hz**，定点格式必须和 RTL 一致（Q2.24 / Q2.30 / 16 bit 饱和）。这样：

- 用户在编辑器里听到的 ≈ 板子听到的；
- 导出 WAV 可以标「模型渲染」，和硬件回传对比就是现成的回归测试；
- 以后改 RTL，跑一遍对比就知道音色有没有变。

### 10.4 浏览器兼容与桌面壳

Web Serial / Web MIDI 只有 Chromium 系支持（Chrome/Edge），且需要安全上下文（`localhost` 或 https）。演示机器如果只能用 Firefox/Safari，就需要本地桥或桌面壳：

| 方案 | 代价 | 何时需要 |
|---|---|---|
| 纯网页 + Chrome | 0 | 演示可控就用这个 |
| Tauri 2 桌面壳 | ~1 人周 | 需要原生串口、文件关联、一键烧录、离线安装包 |
| Node 本地桥 + WebSocket | ~3 天 | 只需要兼容非 Chromium 浏览器 |

**建议**：先纯网页，M4 之后再包 Tauri。烧录用 `programmer_cli`（已装 `V1.9.12.04`）由壳调用，网页本身不碰烧录。

### 10.5 本地优先

「本地编排」按字面实现：工程存 IndexedDB、支持离线打开、PWA 可安装、不依赖任何云服务。这也是和 musiccreator.ai 的差异点之一（它是云端编辑器）。

### 11.1 风险表

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R1 | 固件跑不到设定波特率，或 VCP 吞吐上不去 | 中 | 音频回传降级为 24k 单声道 | E2 实测；不够就降采样或只做遥测 |

| R4 | 16 voice 不够 16 轨同时响 | 高 | 产品预期落差 | UI 明确显示「同时发声上限」；分轨试听 |
| R5 | 后级已上架但参数写死、音色未验收 | 中 | 演示效果 | 先把 env/gd/gw 引出来给上位机；用回传做 A/B |
| R6 | 采样率 48828.125 与 48k 的偏差被听出来 | 高 | 音准被质疑 | 弯音通路顺带做 master tune |
| R7 | 浏览器/驱动在演示机器上出问题 | 中 | 现场翻车 | 提前在同型号机器彩排；准备 Tauri 包 |
| R8 | 事件抖动 >5 ms，节奏听起来不齐 | 中 | 体验 | 实测；必要时加 `delay_us` 调度字段 |

### 11.2 三个先导实验（做完再决定投不投）

**E1 — 枚举（0.5 天）**

```bash
lsusb                      # 期望 0403:6014（FT2232）或 33aa:0120（BL616）
ls -l /dev/ttyACM* /dev/ttyUSB*
dmesg | tail -30
```

判据：出现一个可打开的串口节点；115200 能收到数据。

**E2 — 吞吐与延迟（1 天，需要一个小 bitstream）**

RTL：UART 回环（收什么发什么）+ 计数器流（连续发 `0x00..0xFF`）。
测法：主机侧写一个最小脚本（串口 + 计时即可）连发 2000 帧，量吞吐；发 6 字节量往返。
前提：仓库里还没有 UART 回环的 bitstream，E2 要先做这个最小回环。

判据：

```text
≥ 2.0 Mbps 持续吞吐   → L2（立体声 48.8k）可做
1.0–2.0 Mbps          → L1（单声道/24k 立体声）
< 1.0 Mbps            → 只做遥测，音频走二期
往返 < 5 ms           → 事件链路可用于实时演奏
```

**E3 — 闭环（2 天）**

网页按键 → 协议帧 → `host_link` → `router_system_top` → 出声。
判据：按 16 个键不丢事件；`ALL_NOTES_OFF` 后 50 ms 内静音；拔线再插能恢复。

## 13. 明确不做 / 不承诺

1. **数据面只走 UART**。不引入第二套传输方案；烧录仍用现成工具，但不在数据路径上。
2. **不承诺 32 复音**。新架构 16 槽；真要 32 得回到旧并行顶层或加倍 lane，那是另一个项目。
3. **不承诺跨引擎同时多音色**。含 E2 的轨与 ABC 轨互斥，UI 必须显式提示。
4. **不承诺每轨独立效果器**。后级是全局的。
5. **不承诺上位机 ≤10 ms**。USB 链路是 2–4 ms 量级，且抖动不可控；赛题指标只对本机压力矩阵那条路负责。
6. **不把「电脑渲染的 WAV」当硬件实录**。要么标「模型渲染」，要么用回传流。
7. **不把上位机的 WebGL 可视化当赛题的「FPGA 硬件可视化」**。赛题要的是 FPGA 内部逻辑生成的 LED/李萨如/频谱，那是另一条要求，不能互相顶替。
8. **不做 AI 编曲**。和本项目核心价值无关，首版不碰。

## 14. 待决策

1. **「音频传输」的方向**：是「板子 → 电脑」的录音/监控（本文按这个展开），还是「电脑 → 板子」送 PCM？后者在现有硬件上没有通用输入通路（PT8211 是 DAC；麦克风阵列不算通用音频输入），而且和「FPGA 实时合成」的叙事冲突。
2. **交付形态**：纯网页（Chrome）+ 可选 Tauri 壳，还是必须跨浏览器？
3. **多轨的语义**：必须 16 轨同时发声，还是「16 轨编辑、逐轨/分组试听」？（后者现在就能做，前者受 16 voice 限制）
4. **优先级**：如果只剩 4 周，砍掉「音频回传」还是砍掉「弯音」？本文建议保留弯音（它是乐器表现力），回传降级为遥测。
