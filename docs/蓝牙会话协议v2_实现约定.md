# 蓝牙会话协议 v2：首版实现约定

2026-10-31。本文是开发与测试合同，验收结果另记；不能视为已通过实板验证。

## 线上格式

SLIP 与 CRC-16/CCITT-FALSE 沿用 v1。解码 body：`02 TYPE SEQ:u16LE LEN:u16LE SESSION:u32LE PAYLOAD CRC:u16LE`。CRC 覆盖前十字节和 payload；body=LEN+12，最大44字节，最坏线上90字节。payload 1..32。TYPE=01 MIDI、02 CONFIG、03 CONTROL、80 CONFIG_REPLY、81 CONTROL_REPLY。设备只接收01/02/03；CONFIG最大16，回复80固定3。不会自动降级到v1。所有整数小端。

CONTROL payload的首字节为命令；回复回显请求SEQ。首版命令：

|命令|请求payload（含command）|回复payload|
|---|---|---|
|01 HELLO|01 nonce:u32，header session=0|81 WELCOME: 81 nonce:u32 epoch:u16 caps:u16 max_midi:u8 max_config:u8；header为新session|
|02 CONFIRM|02 nonce:u32|82 READY: 82 epoch:u16 expected_midi_seq:u16|
|03 PING|03 has_midi:u8 last_midi_seq:u16 epoch:u16|83 PONG: 83 state:u8 epoch:u16 expected_midi_seq:u16|
|04 STATUS_GET|04|84 STATUS: 84 state:u8 epoch:u16 expected_midi_seq:u16 reason:u8|
|05 RESUME|05 epoch:u16 first_midi_seq:u16|85 PLAYBACK_READY: 85 epoch:u16 expected_midi_seq:u16|

异步通知（SEQ=0）：86 RESYNC_REQUIRED：`86 epoch:u16 reason:u8`；87 FAULT：`87 reason:u8`。坏控制参数回复`FF original_command result`，result沿用v1的1/2/3/6。旧session控制/业务静默丢弃；非法请求不能刷新心跳。

state：0 WAIT_HELLO，1 CLEANUP，2 WAIT_CONFIRM，3 ACTIVE，4 RESYNC。reason：0无，1 MIDI序号缺口，2 MIDI语法，3 心跳超时，4物理断开，5物理错误/溢出，6协议错误阈值，7处理进度超时。caps bit0会话、bit1心跳、bit2演奏恢复、bit3配置；不宣称EQ或音频后端状态查询已实现。

## 会话、清理与重试

设备32位session计数器在同次FPGA运行期间单调递增，0保留；耗尽后拒绝建立，需复位。复位后计数器重新开始，因此不承诺跨FPGA复位唯一；App见连接/设备复位必须重新HELLO，不能依赖旧会话恢复。nonce用于匹配握手回复，不是认证。

HELLO触发已有来源清音/事件排空/parser及真实后端退休；必须观察maintenance_done后才WELCOME。相同nonce且header session=0的HELLO重试，在CLEANUP不重启清理，在WAIT_CONFIRM/ACTIVE重放WELCOME；新的nonce重建。CONFIRM匹配nonce/session后ACTIVE，重复CONFIRM幂等回READY，不重置序号。等待CONFIRM也有超时。

握手初始epoch=0，expected_midi_seq=0。MIDI payload=`epoch:u16 + 完整MIDI消息`，总长3..32，即实际MIDI最多30字节；CONFIG保持v1字段。当前epoch不匹配帧静默丢弃。当前epoch的MIDI序号必须恰好expected；不自动重发；错误序号触发来源清理并递增epoch、进入RESYNC，保留session。epoch耗尽则撤销会话。清理完成后发送RESYNC_REQUIRED；只接受匹配新epoch的RESUME，再发送PLAYBACK_READY。手机等待PLAYBACK_READY后，以完整MIDI消息重发当前踏板和仍按住的音符，再继续增量演奏。这是逐消息重建，不承诺跨帧原子快照。重复RESUME在ACTIVE仅当epoch及first_midi_seq等于已记录的恢复请求时重放原PLAYBACK_READY，不可倒退设备实际进度。

单个CRC、转义、长度/版本错误、半帧超时只计数丢帧，不撤销。可参数化ERROR_LIMIT和ERROR_WINDOW_CYCLES，窗口内达到阈值撤销；0关闭阈值。配置字段错误不计入。MIDI语法错误触发演奏恢复。framing/break/overflow撤销。STATE下降沿撤销，上升沿等待HELLO。

PING每500ms（手机建议），HEARTBEAT_CYCLES默认2秒；仅匹配当前会话/epoch且字段合法的PING刷新ACTIVE活性，不以持续MIDI代替心跳。PING的last_midi_seq是该字节流中此前已发出的MIDI帧号，has_midi=0表示本epoch未发送MIDI。进度按“已交给业务parser的完整帧”计，比较expected与last+1；队列暂时落后不立即清音，启动PROGRESS_CYCLES超时，追上则撤销计时。MIDI解析语法错误另行触发恢复。模65536比较限制手机未处理在途MIDI少于32768帧。

故障清理仍使用原session_ctrl的真实屏障；控制RX/TX不能受业务parser/config在途或来源quarantine门控。业务缓冲溢出必须产生硬故障，不能静默丢MIDI。硬故障撤销后业务持续被会话层阻止，HELLO仍可到达。配置结果必须绑定提交时会话；新会话在旧配置退休前不能WELCOME，避免旧回复标成新会话。配置重试缓存于维护完成清除。

首版配置重试保证限定在未发生维护的ACTIVE区间。演奏恢复也会清理原parser上下文及重试缓存，因此手机收到RESYNC_REQUIRED时须把未完成CONFIG标为“结果未知”，禁止继续以原请求自动重试；恢复后先核对或以新SEQ重设所需状态。当前仅REVERB_SET有真实后端，属于设置目标状态的命令。状态查询首版只返回会话/epoch/序号/原因，尚未接入实际混响值、菜单来源/通道/权限及音频ready；不能据此宣称音频已可演奏。

## 手机参考代码接入

`web/midi-editor/src/protocol-v2.mjs`导出FrameReader、encodeFrame/decodeBody、packMidi及ReferenceSessionClient；原网页串口仍使用v1，未自动切换。该客户端只生成/消费帧，应用负责蓝牙socket、单写队列、定时器和当前按键/踏板记录。

1. 每次新的逻辑会话生成nonce，构造客户端，串行写入`hello()`；同一次握手超时重试保持nonce。
2. 接收字节持续喂给FrameReader；将完整帧交给`handleFrame`，收到welcome事件后写`confirm()`，收到ready事件后才能写`midi()`或`config()`。
3. ACTIVE中每500ms串行写`ping()`；生成MIDI帧与PING必须遵守同一发送顺序，`midi()`生成的帧不得被静默取消后仍把旧水位发送给设备。配置同一时刻最多一条；超时使用`retryConfig()`，不得自动重发MIDI。
4. 收到resync_required后，清除手机端尚未写入的旧MIDI队列，暂停增量演奏，发送`resume()`；收到playback_ready后再以完整MIDI消息发送当前踏板/按键状态，恢复增量演奏。故障/心跳超时则停止业务，重新HELLO。
5. `heartbeatTimedOut(now)`只报告超时，应用必须据此停止发送；模块不自行开定时器。手机等待首个PONG期间也有超时，不能因尚未收到过PONG永久保持ACTIVE。

参考客户端测试：仓库根目录`node web/midi-editor/tests/run.mjs`，包含已有v1测试、v2编解码/会话测试和独立恢复边界测试。

## 模块边界（固定接口，供并行开发）

`comm_v2_codec`：clk/rst_n/flush；RX字节rx_valid/rx_ready/rx_data[7:0]；分别独立的ctrl_valid/ctrl_ready/ctrl_seq[15:0]/ctrl_session[31:0]/ctrl_len[5:0]/ctrl_payload[255:0]及biz_valid/biz_ready/biz_type[7:0]/biz_seq/biz_session/biz_len/biz_payload；errors[7:0]低5位沿用v1，第5位为已验证帧队列overflow。RX不因biz队列阻塞停止接收控制，控制队列也有限且溢出报错。TX完整帧接口send_valid/send_ready/send_type[7:0]/send_seq[15:0]/send_session[31:0]/send_len[5:0]/send_payload[255:0]到tx_valid/tx_ready/tx_data[7:0]，payload byte0位于[7:0]。参数FRAME_DEPTH=8,CONTROL_DEPTH=4,TIMEOUT_CYCLES=100000000。flush清候选和队列/TX；普通维护不flush该模块。

`transport_v2_link`：对外保持transport_link原接口（flush/pin为原业务维护）；增加maintenance_done、physical_fault、disconnect_event、midi_error输入，cleanup_request输出。内部实例化codec，输出原有业务字节帧流，剥离epoch，输出CONFIG回复v2封装。flush触发清空未提交业务、pin保留当前正在输出帧收束，不清控制通路；maintenance_done是session_ctrl cache_reset脉冲。所有故障/HELLO由cleanup_request单拍请求session_ctrl走真实屏障。参数额外CLK_HZ=100000000,HEARTBEAT_CYCLES=2*CLK_HZ,PROGRESS_CYCLES=CLK_HZ/4,ERROR_LIMIT=8,ERROR_WINDOW_CYCLES=CLK_HZ。protocol_errors输出codec errors供sticky记录，但v2不再交给原session_ctrl做错误隔离。回复队列需独立于控制，发送按完整帧仲裁。active业务输出在maintenance期间禁止新准入，已pin帧收束；旧会话/epoch排队帧需按元数据再次检查。

## 验收范围

v1默认保持既有行为；BT_PROTOCOL_V2=1启用v2蓝牙分支，有线仍v1。先提供可选板级参数，不默认为未验证的新协议。单元及端到端测试须覆盖握手/幂等、CRC丢帧不清音、旧session及epoch拒绝、丢最后NOTE_OFF由PING发现、正常后端背压不误报、隔离时HELLO可达、慢配置期间控制可达、硬故障及超时清理、恢复不重放旧NOTE_ON、配置ACK实际完成、SEQ回绕及转义。尚未实现项必须在结果中明确列出，不得用参考模型结果替代RTL验证。
