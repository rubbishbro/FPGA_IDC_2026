## 1. 结论：我们做的是什么产品

建议定位为：

**面向音乐入门、即兴演奏和音色探索的压力交互式 FPGA 实时合成乐器，配套轻量 MIDI／音色编辑上位机和蓝牙简易控制 App。**

产品的核心不是“再做一个 MIDI 编辑器”，而是把以下过程连接起来：

```text
本机压力矩阵演奏 → FPGA 实时生成声音
                         ↑
电脑：编辑音符、精细调音、保存方案
手机：无线切换音色、调节少量常用参数
```

- 本机是**乐器与音源**：承担演奏输入和实时发声，而非只把控制消息送给电脑。
- 电脑是**编辑工作台**：借鉴 MusicCreator 的 MIDI 编辑交互，但弱化编曲规模，突出硬件试听和频率相关增益。
- 手机是**遥控面板**：减少功能和页面，不再复制一套桌面编辑器。

这是一种已有市场先例的产品组合，不是无人覆盖的空白市场。可争取的差异是“压力交互 + 参数化模态合成 + 直观频谱塑形 + 分层控制”，而不是宣称 MIDI、EQ、物理建模或蓝牙控制本身首创。

## 2. 面向哪些需求设计

以下是根据产品能力和竞品用途提出的**待验证需求假设**。

| 用户／场景 | 想完成的任务 | 对应设计 | 为什么需要，而不只是增加功能 |
|---|---|---|---|
| 音乐入门者、普通爱好者 | 不先学习完整 DAW，也能演奏短旋律、和弦和节奏 | 4×4 压力矩阵、预设音色；可考虑音阶／键位映射 | 将主要操作留在乐器上，减少软件设置步骤 |
| 即兴演奏、排练与展示 | 按下即响，力度变化有反馈，不依赖电脑持续运行 | 本地采集、FPGA 合成、本地音频输出 | 演奏链路不需要经过手机网络或电脑软件音源 |
| 对音色有兴趣的创作者 | 不只是换预设，还能把声音调得更明亮、温暖或突出某些共鸣 | 桌面频率—增益曲线、混响与预设对比 | 将底层模态／滤波参数变成可理解、可试听的音色操作 |
| 轻量旋律创作与练习 | 导入、修改、循环试听一小段 MIDI | 简化钢琴卷帘、力度编辑、速度与循环控制 | 比完整制作软件更聚焦，同时保留音符级编辑能力 |
| 不方便使用电脑的场合 | 演奏前后快速换音色、调音量和混响 | 蓝牙手机 App | 手机用于配置，而不是承担实时音频计算 |
| 教学与工程演示（次级场景） | 观察压力、模态、频率分布与听感的关系 | 状态显示、曲线与可选频谱反馈 | 提高合成过程的可解释性；不等于已具备教学课程体系 |

**优先对象建议：**音乐爱好者和入门级音色探索用户。专业整曲制作、录音棚音源替代不是首版主目标。

需要避免的需求论证：

- “现有 MIDI 编辑器不能实时试听”不成立，MusicCreator 和 signal 均提供播放能力。[S1][S2]
- “现有乐器都必须连接电脑”不成立，MicroFreak、MC-101、Orba 都有本机发声能力。[S4][S5][S6]
- “物理建模产品没有 EQ 或频谱编辑”不成立，Pianoteq 已有模型前均衡及后级 EQ。[S8]
- “采用 FPGA 必然更便宜、更低功耗、延迟优于所有软件”没有本项目的测量与成本证据，不能作为已证实卖点。

## 3. 当前架构支持什么、不支持什么

### 3.1 可以据此提出的产品能力

实现已不再是 Step 1 的“四个独立 engine、RAM 只存状态”方案。正式路径为 `router_system_top → shared_engines_system_top → shared_engines_top`；A/B/C 共用纯计算核，与 E2 二选一，后级默认开启。

| 架构依据 | 产品含义 | 状态／限制 |
|---|---|---|
| `fmap[127:0]`、`excitation_convert` 线性压力映射 | 有 4×4、每单元 8 bit 的输入接口 | 正式前端只取 `fmap[7:0]`，向 A/B/C/E2 的 slot0 注入 x；没有完成 16 键选音、触发和逐键力度闭环 |
| `NUM_SLOTS=16`，逐 voice 系数／状态独立 | 有全局 16 槽的 RTL 基础 | 回归包含小规模冒烟，不等于整机满 16 复音持续可闻、无欠载和低延迟验收 |
| `pure_engine_abc → abc_engine` 与 `e2_engine` | 四种 class 对应两种计算核，ABC 内可按 voice 装载不同系数 | 不能再将“一个核”解释为“只能一个音色”；完整多轨演奏还需激励、事件调度和验证 |
| `sel_e2 = (abc_active == 0) && any(e2_active)` | ABC 与 E2 不同时计算；有 ABC 活动时优先 ABC | 没有自动清音／安全切换机制；不能承诺 ABC+E2 合奏或无缝切换 |
| `shared_modal_ram` 为 4 lane × 9 字段，默认每 lane 深度 320 | 实际 RAM 同时保存系数和状态，可为音色编辑提供后续写入基础 | 不是旧稿的“RAM 仅存动态数据”；单字段写口在 `engine_mux` 中仍接 0，主机不可直接修改 |
| `POST_EN=1`：增益→四段 body biquad→四梳状混响→dry/wet→final | 后级已实现并接入默认路径 | 全局一套；body 固定 instrument 0，env/gd/gw 在系统层固定，尚非用户可调 EQ／ADSR／混响面板 |
| `load/off` 事件口与 `router_frontend` | 可作为后续上位机连接适配的入口 | `load_inst` 2 bit、`rcfg_instrument` 4 bit 尚不统一；frontend 的 load 请求未接正式 loader；UART／BLE 未实现 |
| `linear_modulation.sv` 有多项式占位实现及单测 | 已有独立调制原型 | 未接正式顶层，不能宣称弯音、滑音、颤音或 MPE 已生效 |
| `FFT_spectrumshow/` 有 1024 点 FFT、128 柱、64 帧瀑布核心 | 新增板端音频可视化的实现基础 | 尚未接主合成链，且本轮链级测试编译失败，不能称整机实时频谱已完成 |

首版从单轨／单音色开始仍可用于控制开发范围，**但这不再是硬件必须单音色的结论**。ABC 内不同 voice 可加载不同音色；B 的持续激励等旧前端已归档，不能只凭系数独立就承诺吉他、钢琴、长笛的完整联合演奏。

### 3.2 本轮验证与未闭环项目

- 重跑 `sim/run_core.sh`：**21 项全部 PASS**，包含 signed 增益／递推、E2 首次装载、后级握手、数据顺序与系统冒烟。
- 后级已改为**一个 engine 样本 → 一次 post 握手 → 一个对应输出**，旧版的 32 激励／1024 零尾音诊断循环已移除；不能再用它推算正式样本周期。
- 当前保留的 `router_probe.tr` 为 **100.063 MHz、setup/hold 违例 0/0、最差 setup slack +0.006 ns**；PnR 资源为 Logic 9,647、Register 6,047、BSRAM 113、DSP 56。它是小型测试 ROM 的 3-I/O 探针，不是主音频板级顶层，也不是本轮新跑出的报告。
- `FFT_spectrumshow/sim/chain_tb.v` 本轮 Icarus 编译失败：`spectrum_map.v` 引用了未声明的 `xk_re_r`、`xk_im_r`。其 README 中的历史 CHAIN PASS 不能代表当前提交可复现；另有 bin/bar 流水对齐等已知问题。
- 主合成核到音频串行输出、传感器实板、FFT 跨域接入、主机链路均需分别验收。本轮未改 RTL，也未修复上述阻塞。

### 3.3 赛题要求与用户价值要分开

仓库赛题摘录要求至少两个独立可控演奏维度、基础复音数 ≥4，以及控制输入到音频输出总延迟 ≤10 ms；拓展项包括 ≤5 ms、更多表情维度、效果器与手机联动。

- **这些是要求，不是现有测量结果。**验收必须测完整传感、扫描、调度、合成和音频输出链路。
- “有 8 bit 压力”不自动证明具备两个独立控制维度，应明确并演示选音／位置与力度等维度能独立操作。
- 16 voice 不满足“复音数 ≥32”这个拓展分支；若走模态并行等其他分支，应按赛题统计规则举证，不能把模态数直接当作复音数。
- 当前架构包络和调制的具体实现，仍需对照赛题的 ADSR、实时变调要求核查，不能只因预留接口就判定满足。
- 上位机可以离线准备参数、编辑 MIDI，但最终演奏音频应由 FPGA 实时生成，不能由电脑渲染后推流冒充硬件合成。

依据：`reference_agent_readfirst/competition_requements_most_important.md`。

## 4. 功能相近产品的情况

这些产品分别对应编辑、演奏、音色设计、移动控制等子需求，不宜作为完全同类整机直接排名。

| 产品 | 类别与已公开功能 | 与我们重合的需求 | 对我们的启示与边界 |
|---|---|---|---|
| **MusicCreator.ai MIDI Editor** [S1] | 在线 MIDI 编辑；官网列出导入／导出、SoundFont、WAV 导出、Web MIDI I/O、速度及拍号编辑，并宣传 AI 辅助 | 轻量音符编辑、试听、外部硬件连接 | 可借鉴编辑流程，但网页声音模块不等于 FPGA 音源；“AI”实际效果本次未验证，不应直接纳入需求 |

### 4.1 对给定参考网页的具体取舍

MusicCreator 官网页面可确认的宣传功能包括 SoundFont、WAV 导出、Web MIDI I/O、速度与拍号编辑。**本次主要核对公开页面，未操作完整编辑器，不将页面文案当作实测结论。**

| 参考功能 | 我们的建议 | 原因 |
|---|---|---|
| MIDI 导入、音符与力度编辑 | 保留基本能力 | 服务练习片段、演奏记录修改和硬件试听 |
| 多轨完整编曲 | 可保留多轨编辑；先实现单轨试听，再验证 ABC 分组联合播放 | 编辑轨数不受核选择限制；板端共享 16 槽，ABC/E2 互斥，完整联合演奏尚未验收 |
| 速度、循环播放 | 保留 | 对短片段试听很实用 |
| 曲中复杂变速、变拍号 | 后续再做 | 不属于音色控制的首要价值 |
| SoundFont | 不作为板端必备能力 | 当前板端使用合成参数，不是 SoundFont 播放器 |
| WAV 快速导出 | 暂缓承诺板端音色导出 | 需要 FPGA 音频回传／录音链路；电脑 SoundFont 离线渲染不代表 FPGA 实际输出 |
| Web MIDI I/O | 视实际传输方案选用 | USB-UART 不会自动被浏览器或系统识别为 MIDI 设备 |
| AI 旋律、自动优化 | 不纳入首版 | 与当前硬件音源的主要价值无直接关系 |
| 频率—增益曲线 | 新增重点 | 让桌面端从通用 MIDI 编辑器变成该乐器的音色工作台 |

signal 与该页面列出的基础功能较接近，而且有可检查源码，适合列为技术预研对象；**仅凭功能相近不能推断两个产品存在代码或商业关系。**

## 5. “频率相关增益”应如何定义

当前表述至少有三种含义，不能混为一项功能。建议先用下表确定语义，再决定实现。

| 含义 | 改变什么 | 适用目的 | 首版建议 |
|---|---|---|---|
| **输出频段均衡 EQ** | 对合成音频的低／中／高频等频段做增减益 | 调整体明亮度、厚度，适配不同播放设备 | 通用方案，优先评估 |
| **逐模态频谱塑形** | 根据每个模态实际频率调整该模态的幅度／输出权重 | 更直接地改变音色的共鸣结构 | 更贴合本项目特色，可作为进阶模式 |
| **按音高补偿音量** | 根据所按音符的基频，对整个音符施加增益 | 平衡高低音响度 | 单独命名为键区／音高响度补偿，不称为普通 EQ |

### 5.1 推荐的用户界面

- 桌面基础模式：先考虑 3 段 EQ；低频／中频／高频增益可调，是否开放频率与 Q 取决于硬件预算。
- 桌面进阶模式：对数频率横轴、dB 增益纵轴，少量控制点编辑曲线，支持旁路、复位和 A/B 试听。
- 手机：复用桌面保存的音色方案，或只保留“明亮／温暖”等宏参数；不要另建不兼容的参数语义。
- 频谱分析显示与增益曲线编辑是两件事：已有独立 FFT 可视化核心，但编译阻塞、PCM 抽头、100 MHz→33.3 MHz 跨域及联测仍待完成；电脑实时频谱还需回传通路。

### 5.2 与新 FPGA 架构衔接的注意点

**方案 A：输出 EQ。**已接入的 `body_biquad` 实际为四段级联，但系数来自 ROM，`post_chain` 固定 `BODY_INSTRUMENT=0`，没有运行时系数写口。不能把这四段现有腔体滤波直接算成四段可调用户 EQ。若保留腔体并独立增加三段 EQ，需要新增／复用滤波计算、参数写口和一致性提交，并重测周期及 P&R。当前 body 位于混响前；若另加总输出 EQ，须明确放在混响前还是后。

**方案 B：逐模态塑形。**设曲线在第 k 个模态频率处为 `D(f_k)` dB，可构造独立权重：

```text
w_k = 10^(D(f_k) / 20)
```

它表示幅度权重，不是频率变化或阻尼变化。对 A/B，可评估对输入增益 G 的映射；但 C 的初始 seed、E2 的输出权重等具有不同语义，不能对所有 engine 机械地“把 G 乘一下”。只改激励增益也未必会立即改变已经发声的模态，需明确“下次触发生效”还是“当前声音连续更新”。

共同约束：

1. 当前 loader 从 `.mem` 初始化的系数／index ROM 取参数，再将整条 9×32 记录写入共享 RAM；尚不能把它称为外部 flash 流式系数接口。RAM 已存系数，但 `co_we` 在 mux 层关闭，若开放主机编辑须增加写入仲裁／影子提交，不能直接并发覆盖正在计算的状态。
2. 上位机可计算控制参数和校验系数，但实际滤波／音频合成仍在 FPGA；router 只解析、选择和调度，不承担 DSP 乘法。
3. 先限制可调范围，再验证浮点参考、定点量化、稳定性、峰值余量与饱和。增益限幅不能单独证明混音不会溢出。
4. 多段系数更新需要一致性提交；直接切换或逐项更新可能产生爆音和瞬态不稳定。不要未经验证直接线性插值 IIR 系数；可考虑受控参数过渡或双路径交叉淡化。
5. 当前 `dry_wet_mix` 是 `(dry*gd + wet*gw) >>> 15` 加舍入／饱和，不会除以 `gd+gw`；系统默认 gd=gw=0.5。开放参数时应约束权重和／做显式归一化，并独立验证 EQ、多声部及混响的峰值安全。

**对产品差异的判断：**Pianoteq 的 Main Equalizer 已在计算声音前修改模型，另有后级参数 EQ。[S8] 因此“模型前频率增益”也不是空白；本项目可以强调在自研压力乐器上的简化交互、硬件实时实现和参数可视化。

## 6. 电脑、手机与本机的功能分工

以下是产品规划，不等于接口已开放。电脑链路方向已在[上位机可行性分析](上位机可行性分析.md)收束为 UART／Web Serial；协议仍是草案，手机 BLE 方案未定。

| 功能 | 本机 FPGA／交互 | 电脑上位机 | 手机蓝牙 App |
|---|---|---|---|
| 实时演奏与发声 | 核心职责 | 发送编辑／测试事件，声音由板端生成 | 首版不作为主要演奏输入 |
| 音色选择 | 应能脱离电脑完成基本演奏；切换入口待定 | 完整预设列表 | 常用／收藏预设 |
| 压力校准与力度曲线 | 当前只实现首单元线性映射；校准／曲线待补 | 完整设置、查看原始值 | 最多提供简单灵敏度选项 |
| MIDI 片段编辑 | 不承担图形编辑 | 基本卷帘、力度、导入导出 | 不做 |
| 循环试听 | 接收有界事件，执行发声 | 首版可由电脑负责播放时序 | 首版不承诺曲目／循环控制 |
| 频率相关增益 | 执行选定 DSP／权重方案 | 曲线或多段控制、旁路与对比 | EQ 预设或少量宏参数 |
| 混响与主音量 | 已有全局后级，但需先开放固定参数 | 详细控制（规划） | 常用控制（规划） |
| 配置保存 | 持久化策略待定义 | 优先保存项目／patch 文件 | 收藏／加载已有方案 |
| 状态反馈 | 提供当前配置及能力信息 | 详细状态与调试 | 连接状态和关键参数 |
| 音频录制／WAV | 需要额外采集回传链路 | 后续评估 | 不纳入首版 |

### 6.1 桌面 MVP

建议最小闭环为：

**连接硬件 → 选择音色 → 演奏／导入 MIDI → 修改音符和力度 → 调频率增益与混响 → 保存方案。**

分阶段实现：先打通 UART 事件和单轨试听，再考虑 ABC 内分组播放、后级参数开放与频率塑形。多轨编辑本身不必禁止；播放前检查全局 16 槽预算、ABC/E2 冲突、可用音色及支持的控制器。保留撤销／重做、旁路、恢复默认等基本功能，不要将任意导入 MIDI 当作完整 GM 音源播放。

电脑端的可编辑轨道数、MIDI 16 通道、FPGA 16 voice 和四类 engine 是不同概念，UI 和报告中要分别表达。

### 6.2 手机 MVP

控制在三个页面即可：

1. **设备**：扫描、连接、断开、连接状态与能力识别。
2. **音色**：当前音色、预设／收藏切换。
3. **控制**：主音量、混响量、少量音色宏参数；可加经过确认的八度／移调功能。

蓝牙以配置和控制数据为主，不默认传 PCM 音频，也不默认支持手机扬声器监听。若电脑负责播放 MIDI，手机上的播放按钮还需要控制电脑或板端事件播放器，不能只加一个按钮就认为具备该能力。

### 6.3 通信与一致性

- 标准音符／常规控制可评估 MIDI；曲线、patch 和能力查询可能需要 SysEx 或自定义配置协议，尚不冻结选择。
- 标准 BLE MIDI 与自定义 BLE GATT 是不同方案；“有蓝牙串口模块”不等于自动具备手机通用 BLE MIDI 兼容性。
- 电脑与手机共享参数定义、单位、范围和协议版本，手机只是更少的可见控件。
- 同时连接时要有明确的控制权或冲突策略；参数以设备确认值回显，重连后同步，避免两端显示不同。
- 本机演奏不等待手机回包；配置流量不能阻塞发声。若支持无线 Note On/Off，则另测延迟分布、拥塞、断连及卡音恢复，不能套用本机 ≤10 ms 的结论。

## 7. 建议的差异化表述与验证

### 可以主张的方向

1. **软硬件分工清楚**：FPGA 负责声音，电脑负责精细编辑，手机负责便捷配置。
2. **围绕压力交互设计**：已有线性激励转换原型；逐键选音、触发、校准与连续表情仍需完成，不能将首单元注入说成完整压力乐器。
3. **面向听感的频谱塑形**：不用直接理解每个模态系数，也能通过曲线和预设改变音色。
4. **参数化实时合成路线**：离线从素材提取参数，演奏时不依赖大段 PCM 回放；这是一种技术选择，不自动代表高于商业音源的音质。

### 暂不应使用的宣传

“全能音乐工作站”“四引擎同时合奏”“完整 GM／SoundFont 兼容”“专业级真实乐器复刻”“零延迟／蓝牙零抖动”“首创 EQ”“已支持 MPE”。

### 下一步验证，不直接扩大功能范围

| 要验证的假设 | 建议方法 | 形成的证据 |
|---|---|---|
| 简化交互比通用软件更容易完成目标任务 | 邀请少量入门者与有经验用户，完成选音色、改短旋律、调明亮度、保存方案 | 完成率、耗时、错误及学习障碍；小样本不能外推市场规模 |
| 频率增益确实提供有用的音色变化 | 同一 MIDI、匹配总体响度进行原始／EQ／模态塑形 A/B | 避免将“更响”误判成“音色更好” |
| 手机少功能足够 | 观察离开电脑后的常用操作 | 决定哪些控件必须保留，而不是复制桌面 UI |
| 本机实时性满足目标 | 测输入动作到实际音频输出；覆盖满复音和配置更新 | 延迟及抖动数据、欠载情况 |
| 切换音色与无线断连可接受 | 有尾音时跨引擎切换、反复重连与连续调参 | 截尾／爆音／卡音及恢复行为 |

本次没有调研可比地区售价、销量、BOM、电池续航或功耗，暂不能得出“更低价”“更便携”或具体市场容量结论。

## 8. 可用于设计报告的需求分析草稿

> 本项目面向音乐爱好者在即兴演奏、基础音乐创作和个性化音色探索中的需求，拟设计一套以 FPGA 为实时发声核心、以压力矩阵为演奏入口的多音色电子乐器。现有在线 MIDI 编辑工具提供方便的音符编辑与试听能力，便携合成器和智能乐器则提供本机演奏、音色切换及移动端配置，说明这些需求已有成熟产品覆盖。本项目不以替代完整数字音频工作站为目标，而是聚焦演奏交互与参数化音色设计的结合：通过 FPGA 实时合成降低对电脑软件音源的依赖，配套轻量上位机完成 MIDI 片段编辑、频率相关增益和音色方案管理，并规划通过蓝牙手机 App 提供预设切换、音量及效果量等简易控制。系统的复音、延迟、压力响应和音色处理效果将通过仿真与整机测试分别验证。
