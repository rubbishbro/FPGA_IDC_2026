# mod1逐声部调制预算（2026-11-03）

已将mod1改为与mod0一致的逐声部start/busy/done任务。`MOD1_MODES_PER_JOB` 控制每次更新的前N个模态；不是轮转分块，也不是一次处理N个声部。其余模态保持名义系数。扫描时默认值为4；依据本次结果，当前暂定6，TODO：听感还需要验证。

调制器读取原P1T1参数表，写回既有ca_a12_a/b。pitch_a12_a/b已删除，没有新开系数RAM，参数表不拆分且引擎不读参数表。保留不可变基值、斜率、上下界和tag。旧pitch_bank观测口恒为0，不再选择RAM或全局翻转。

安全窗口：本帧该声部引擎退休后才能启动；以最近采样间隔核对剩余周期，给任务预留6N+20拍（包括调度余量），确保写回及频率比提交在下一帧激励快照前完成。窗口不足只延后调制，不等待或暂停音频。轮询加服务轮次标记避免后部声部饿死。当前持续乐器每组退休都会登记请求，包括MIDI关闭压力调制时的名义系数重建。

## 测试条件

- 50 MHz、每帧1024拍（48,828.125 Hz），16声部、每声部48个有效模态、物理64槽。
- 小提琴普通ENG1激励路径、小号TDM激励路径。真实部署系数/包络/周期，扫描时通过测试台预装载，生产router/engines/excitation均正常执行；不含Flash串行加载时间。
- 每档320帧，每帧改变全部16个声部压力，314个稳态帧计入吞吐范围。每档检查系数算术、实际引擎系数读值、限额外不写、禁止当前声部计算期间写系数、禁止任务跨采样边界、全部声部最终被服务和非零音频。
- 单作业耗时从mod_start接收到该声部pitch_commit，实测为6N+7拍；busy释放另需ACK/握手，调度余量已包含在窗口检查内。

## 如何理解“藏在引擎计算中”

1. **逐组不积压：上限3。** 对前7组，在下一组引擎退休时，上一组的两个声部调制均已完成；N=1/2/3的相邻组迟到检查均为0，N>=4开始积压。
2. **严格全部藏在最后一组引擎结束之前：本调度不存在这样的N。** 最后一组的请求本来就在它自己退休后产生。N=3仍有最大55拍（1.10微秒）的末尾调制工作，N=4为109拍。它利用帧内余量，不延迟音频输出。
3. **每帧16声部都更新且音频不等待：两种路径共同上限6。** 小提琴可到8；小号从7开始无法每帧服务全部声部。上限6单声部43拍。
4. **大N也不会因调制阻塞音频，但更新频率下降。** N=48时，小提琴每帧1–3声部、最大9216拍（184.32微秒）更新间隔；小号每帧1–2声部、最大13312拍（266.24微秒）。轮次服务保证没有声部长期饿死。

这些界限只针对上述固定采样节拍、资源、声部数和当前实现。它们是周期级仿真结果，不是物理Fmax，也不是减少高模态调制后的听感验收。N限制会改变音色内不同模态的音高关系，需另行试听。
