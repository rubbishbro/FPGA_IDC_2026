# PNR 60% 卡住：资源对比与受控复现（2026-11-02）

审查对象：`0e421502`（当前 HEAD，LED 像素缓存改同步 RAM + 共享半径计算）及其上一个可综合版本 `99762fbe`。本轮实际重跑了综合和两组布局布线，未修改生产 RTL/约束，未烧录。

## 结论

1. **当前版本的 FF、LUT、MUX 都低于上一次成功的整板实现，ALU 只高约 4%。** 以 11-01 15:12 通过时序的 `led_joy_board` 为基线：FF 37,936→33,687（-11.2%），LUT 61,332→50,009（-18.5%），级联 MUX 16,775→4,251（-74.7%），ALU 13,936→14,528（+4.3%）。逻辑总量 75,268→64,537（-14.3%）。
2. **60% 不是器件容量不足。** 当前版本实测布局后 CLS 47,385/69,120（69%），Logic 48%、Register 25%；成功版本曾用到 CLS 78%~80%。当前占用反而更低。
3. **直接原因是 `route_option=1`，不是 place。** 同一份当前网表：`place3/route2` 的 Phase 1 仅 2 分 40 秒，布通并通过时序；保持 `place3` 只把 route 改成 1，Phase 1 超过 11 分钟仍停在 60%；`place1/route1` 则超过 15 分 20 秒。route1 单独就足以复现停滞。
4. **11-02 的 60% 停滞与策略默认值改动直接相关。** `4bcee5f2`（11-02 03:21）把 `build.tcl` 默认从工具的 3/2 改成 1/1，而 route1 正是会卡的模式；此前 01:33 的失败运行和 11-01 的成功运行都用 3/2。此后 02:48 与 04:11 两次运行都在 1/1 下停在 60%。
5. **较早的 77k 网表确实过满。** 01:33 那次 Logic 78,015、CLS 84%，用 3/2 也在 Phase 1 跑了 67 分钟后以 349 条未布通结束。当前 64.5k/69% CLS 是后续削减的结果，已经跨回可布通区间。
6. **ALU 仍是唯一高于成功基线的资源**，集中在包络、混响、激励和新增配置/通信逻辑；它不是本次 60% 停滞的直接原因（当前物理 ALU 15,218，成功 14,595），但会压缩时序余量（当前 core Fmax 53.126MHz，目标 50MHz）。

## 数据口径

- 综合数字来自 Gowin Synthesis 1.9.12 官方报告或同一份 `.vg` 网表原语统计：LUT 为 LUT1..LUT4（官方报告含 INV），FF 为 DFF/DFFCE/DFFRE 等，ALU 为 ALU 原语，MUX 为 MUX2_LUT5..MUX2_LUT8 级联原语。
- **MUX 不是独立物理资源**：它由 LUT/CLS 实现，单列是为了观察宽选择树。不能把 MUX 数与 LUT 数直接相加当作器件占用。
- 物理数字来自 `instrument_board.rpt.txt`；综合与物理的 ALU/FF 会有映射后少量差异，跨版本比较以同口径为准。物理报告的 DSP/BSRAM 是器件折算后的计数，与综合网表的 MULT/BSRAM 原语不是同一口径（例如成功版本网表 DSP 102，物理报告 172），因此只在同表内比较。
- 基线用 `led_joy_board`（11-01 15:12，setup/hold 0、Fmax 58.532MHz），因为它是最新可读且时序通过的整板实现；`volume_plus12_20261101`（11-01 00:27，Fmax 50.164MHz）作为更早基线附在表中。

## 60% 到底停在哪

Gowin 的进度条中 `[60%] Routing Phase 0 completed` 表示 Phase 0 已完成，进程随后进入 **Routing Phase 1（迷宫/rip-up 重布）**。卡住位置都在 Phase 1 内部：

| 运行 | 网表规模 | 策略 | 60% 停留 | 结局 |
|---|---|---:|---:|---|
| `024823` | 77,337 Logic / 42,848 FF | 1/1 | 约 24 分钟 | 用户 SIGTERM，无布通结论 |
| `041102` (`99762fbe`) | 66,657 Logic / 36,575 FF | 1/1 | 约 6 分钟 | 进程退出，无 exit_code，不能据此判定死循环 |
| 本轮 HEAD 对照 A | 64,537 Logic / 33,687 FF | 3/2 | **2 分 40 秒完成 Phase 1** | 布通，位流生成，时序通过 |
| 本轮 HEAD 对照 B | 同上 | 3/1 | **>11 分钟仍停在 60%** | 为释放资源终止 |
| 本轮 HEAD 对照 C | 同上 | 1/1 | **15 分 20 秒仍停在 60%** | 为释放资源终止 |

只改 route（3/2→3/1）就复现停滞，说明 `route_option=1` 是必要条件；`place_option=1` 不是必要条件（1/2 未跑，不影响该结论）。3/1 与 3/2 使用相同网表、相同 CST/SDC、相同 place 选项，差异只有 route。

GDB 采样（11-01 及 11-02）都落在 `PathRoute::mazeRoute`/`getHeapHead`，CPU 约 99.7%，是路径搜索本身耗时，不是崩溃或内存耗尽。当前 69% CLS 的同网表在 3/2 下 2 分 40 秒完成；相同 place3、仅把 route 改成 1 就超过 11 分钟，说明停滞由 `route_option=1` 的搜索策略触发，而不是逻辑量放不下。route1 的“尝试更好布线”质量模式在本设计上会进入极长的 rip-up 循环，不能靠继续等待解决。

## 建议

1. **立即恢复成功版本的 PnR 策略**：`BOARD_PLACE_OPTION=3`、`BOARD_ROUTE_OPTION=2`，或把 `build.tcl` 默认改回 3/2。本轮已用当前 HEAD 网表验证：布通、位流生成、时序验收通过。**关键是 route 用 2**；place 3 已验证，若未来想用 place 1，应先单独跑 1/2（`build/pnr_matrix.sh 1 2`），不要在 route1 上继续等。
2. **保留本轮资源削减**（LED RAM、单参数表、curve RAM）。当前 CLS 69% 已从失败时的 84% 降下来，是 3/2 能快速布通的前提。
3. **后续再处理 ALU 热点**：包络 2,560、激励 3,136、混响 1,428。优先做可证明等价的共享/逐槽调度，不要用删声部、截位或取消必要复位来换资源；当前 core Fmax 只有 53.126MHz，余量约 3MHz。
4. **高扇出控制仍需单独治理**：当前核心复位网约 9,277 个端点、像素域复位 4,463、`xmap_valid` 1,796 个 CE、`active_play` 初始化 RESET 1,281。它们是局部拥塞和时序压力的来源，但不是本次 60% 的直接开关。
5. 若还要进一步压布线时间，先固定 3/2 重跑完整 `build.tcl`（含验收），再逐项改 RTL，每次只动一块并保留 A/B 网表。

## 如何排查（固定网表，矩阵法）

不要每次重综合。用同一份 `.vg`，只改 place/route，一次一个变量：

```bash
# 已知可布通基线
build/pnr_matrix.sh 3 2
# 只改 route：验证 route1 是否单独致卡
build/pnr_matrix.sh 3 1
# 只改 place：验证 place1 的影响
build/pnr_matrix.sh 1 2
# 原始组合
build/pnr_matrix.sh 1 1
```

每个默认 1800 秒超时，结果在 `build/pnr_matrix_p<place>r<route>/`。判定表：

| 3/2 | 3/1 | 1/2 | 结论 |
|---|---|---|---|
| 通过 | 卡 | 通过 | `route_option=1` 是原因（本轮 3/1 已卡，3/2 通过） |
| 通过 | 通过 | 卡 | `place_option=1` 是原因 |
| 通过 | 卡 | 卡 | 两者都会触发，固定用 3/2 |
| 卡 | 卡 | 卡 | 网表/拥塞问题，进入 CLS/扇出分析 |

每个点记录：到达 `[70%]` 的时间、`PR0004` 条数、CLS%、Fmax、时序是否通过。

现场确认是否真卡：

```bash
tail -f build/<run>/instrument_board/impl/pnr/instrument_board.log
ps -eo pid,etime,pcpu,rss,args | grep gw_sh
gdb -p <pid> -batch -ex 'thread apply all bt' 2>/dev/null | head -30
```

- 停在 `[60%] Routing Phase 0 completed` 表示在 Routing Phase 1。
- CPU 约 100%、RSS 约 2.1GB 是正常路径搜索，不是 OOM。
- 栈落在 `PathRoute::mazeRoute`/`getHeapHead` 即迷宫搜索本身。
- 超过基线（2 分 40 秒）4~5 倍仍无 `[70%]`，按卡住处理，不要无限等。

只有矩阵全部卡住才查拥塞：

- 先看 CLS% 和区域分布（GUI floorplan/congestion），不能只看 LUT%。
- 高扇出网：核心复位 9,277、像素域复位 4,463、`xmap_valid` 1,796 CE、`active_play` 初始化 1,281 RESET。
- 跨区域宽总线/大表：参数表 1,280 位、LED 帧缓存、pixel mailbox。
- 处理顺序：大表 RAM 化 → 拆复位/CE → 共享 ALU → 再评估布局。

布通后必须跑时序验收：

```bash
python3 rtl/platform/tang_mega_138k_pro/check_board.py \
  --timing build/<run>/instrument_board/impl/pnr/instrument_board.tr \
  --out build/<run>/acceptance.json
```

FS 生成不等于时序通过；验收失败不要烧录。

## 验证边界

- 本轮 3/2 布线使用 `0e421502` 的综合网表、同一 CST/SDC，通过最小 Tcl 调用 `run pnr`；位流已生成但未烧录。
- 时序验收由 `check_board.py --timing` 执行并通过：setup/hold 违反 0，recovery +10.351ns、removal +0.264ns、min pulse +4.3ns、max_delay 最差 +7.324ns；clk_core 53.126MHz、clk_pix 37.305MHz。
- 1/1 对照在 60% 停留 15 分 20 秒后终止；3/1 对照在 60% 停留 11 分钟后终止。结论是 `route_option=1` 显著更慢并停在 60%，不是形式证明永不完成。
- 资源和时序数字只对应上述固定网表/约束；换 RTL 或约束后需重跑。
