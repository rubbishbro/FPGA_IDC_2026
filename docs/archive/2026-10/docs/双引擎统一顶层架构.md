# 双引擎统一顶层与共享缓冲区架构（讨论稿）

> **已归档（2026-10-20）**：本文保留推导与证据；当前结论和入口见[工程汇报](../../../工程汇报.md)。

**日期**：2026-10-19  
**状态**：讨论稿，未冻结；只读分析，未改 RTL/ROM/NPZ。  
**范围**：把现有两套合成实现放到同一个核心顶层下：

- **ENG1**：`rtl/core/modal_engine` + `modal_poly_bank` + `body_filter`，
  32 声部 × 48 模态、4 lane、三系数 `(a1,a2,G)`、Q2.30、当前生产路径。
- **ENG2**：`rtl/simsynth/modal_engine7` + `modal_voice_top`，
  7 乘法器并联、物理状态 `(q,q̇)`、8 声部/引擎、A/B ping-pong bank、YW=64/YF=40。

目标结构（用户提出）：

```text
RT <--> BUF[(数据 / 结果 / 系数)]
          ENG1[合成引擎 1] <--> BUF
          ENG2[合成引擎 2] <--> BUF
          BUF --> POST[后级合成与共鸣腔]
          POST --> RVB
```

**结论先说**：**可以复用一个核心顶层 shell；BUF 要分层看：系数源可以按最大位宽共享，
每采样工作状态/结果不建议共享。** 正确的做法是：

1. **系数源/表**可以做成一份 **max-width（224/256-bit）共享 BUF**，按 `engine` 分 region；
   ENG1 只读低 72 bit，ENG2 读全部 224 bit，“另一个 engine 不读”就是 region 隔离；
2. **每采样工作状态**（y1/y2 或 q/q̇）留在各引擎本地 bank：两个引擎每个采样都要
   读写自己的 state，单端口/1W1R 的访问次数不够；
3. 顶层提供**命令 FIFO、系数暂存、结果 ping-pong、状态**，统一
   **PLL/reset、48.828 kHz tick、格式对齐、POST/RVB、输出 FIFO/I2S**；
4. ENG1-only 必须保持逐位不变；ENG2 作为并行第二引擎接入；先分测，再混音。

这样既能实现用户图里的“BUF + 两引擎 + POST + RVB”，又不会把两个引擎的
时序/存储架构绑死。

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 能不能复用一个顶层？ | **能**：一个 `synth_top` 核心 shell + 一个薄板级 `top`（PLL/引脚） |
| BUF 能不能是一块共享内存？ | **系数源可以**（max-width、按 engine 分 region，note-on 读）；**每采样 state/result 不建议**：两个引擎每采样都读写自己的 state，单端口/1W1R 次数不够 |
| 两个引擎能否并行？ | **能**：ENG1 1508 周期、ENG2 480 周期，跑在不同 DSP/RAM 上，共用 2048 周期 tick；不是相加 |
| 结果怎么合？ | ENG1 Q2.30、ENG2 YF=40；先统一到 Q2.30（或 Q2.40），再做每引擎增益/求和 |
| POST 怎么放？ | 复用 `body_filter`；建议支持**每引擎 bypass/body select**，不要默认把吉他箱体套到所有引擎 |
| RVB 放哪？ | POST 之后新增，建议 **send/return 干湿混合**，不要 100% 串行湿声；先留 bypass |
| 资源够不够？ | 8 声部 ENG2：约 103 BSRAM / 42 DSP / 18.7k logic；16 声部 + RVB 约 160–168 BSRAM / 72–78 DSP，器件 340/298，**面积可行** |
| 最大风险 | **时序**（ENG1 只有 +1 ps，ENG2 104 MHz 也只剩 4%）；其次是 **格式对齐**、**ENG2 的 ROM/loader/allocator**、**BUF 仲裁** |
| 建议路线 | 先 shell + ENG1 逐位不变 → ENG2 独立接入 → 结果 ping-pong/混音 → POST → RT/loader → RVB |

## 1. 两个引擎的现状（为什么不能简单合并）

### 1.1 接口与数据格式

| 项 | ENG1（生产） | ENG2（物理原型） |
|---|---|---|
| 递推 | `y = G·x − a1·y1 − a2·y2` | `q' = a11 q + a12 v + gq x`；`v' = a21 q + a22 v + gv x`；`y = wo·q` |
| 系数/模态 | 72 bit：G Q2.24(26) + a2 UQ0.24(24) + a1 Q2.20(22) | 7 × 32 bit：a11/a12/a21/a22/gq/gv/wo，逐字段编译期 Q |
| 状态/模态 | y1/y2 各 Q2.30(32)，打包 64 bit | q/q̇ 各 32 bit（QW/VW） |
| 激励 | 每声部一个 32-bit `x_vec`，共享给该声部所有模态 | 每声部一个 `x`，按采样存 `x_ram`，可块处理 |
| 输出 | 64-bit `mix_sum`，Q2.30；另有逐声部 `voice_sum` | 64-bit `Y`，YW=64 / YF=40；逐声部结果 RAM |
| 控制 | `load_valid/ready` + `sample_valid/ready` + `active_mask/n_modes_vec/x_vec` | `start/n_samples/n_modes/done/busy` + 5 组 SRAM 口 |
| 存储 | 32×48 工作缓存 + A ROM，engine 49 BSRAM | 8 声部 × 48 × 7 字段 + 状态 + A/B 双份，48 BSRAM |
| 吞吐 | 满载 1508 周期/采样 | 8 声部 × 48 模态 ≈ 480 周期/采样 |
| 时序 | 100 MHz 基线，setup 最坏 +1 ps | 独立 PnR 104 MHz（slack +0.097 ns） |
| 成熟度 | 生产网表、整链、实板 | 算术/引擎/声部层逐位验证；**缺真实系数 ROM、loader、allocator** |

### 1.2 关键差异

1. **算法不同**：ENG1 是二阶 IIR 的 `(a1,a2,G)`；ENG2 是物理 `(q,q̇)` 状态、
   7 个系数/模态。两者的系数不能互换，也不能共用一份 coefficient word。
2. **存储组织不同**：ENG1 的 72-bit 工作缓存按 lane 单端口；ENG2 把 7 个字段
   拆成 7 个 32-bit 阵列，加 A/B 双份 bank。把两者塞进一块共享 RAM，会破坏
   ENG2 的“7 字段并行读 + 双写口”和 ENG1 的“单端口 72-bit 三访问”结构。
3. **输出标度不同**：ENG1 是 Q2.30，ENG2 是 YF=40。直接相加会差 10 个二进制位
   （约 60 dB），混音前必须对齐。
4. **成熟度不同**：ENG1 是生产路径；ENG2 目前是“算术/引擎验证原型”，
   `rtl/simsynth/README.md` 明确写了“系数 ROM 的真实内容、note-on 装载、
   声部分配器”还没做。统一顶层不能把这些缺口一起“封装掉”。

## 2. 顶层边界：什么共享，什么不共享

### 2.1 应该共享

| 共享项 | 说明 |
|---|---|
| PLL / reset | 复用 `clock_reset.sv`：50 MHz → 100 MHz core + 12.5 MHz audio；锁定后释放 `rst_n` |
| 采样 tick | 用 `audio_transport.core_sample_pulse`（48.828 kHz，2048 周期/sample）作为唯一 tick |
| 结果缓冲 / 混音 | 两引擎结果写 ping-pong，POST 读上一采样；统一 Q 格式与每引擎增益 |
| 系数源/表 | 可以共用一份 max-width（224/256-bit）BUF，按 engine 分 region；loader 读自己的 region |
| POST（body/cavity） | 复用 `body_filter.sv`；按引擎 class 选择 body/bypass |
| RVB | 新增后级，send/return；先 bypass |
| 输出适配 / TX FIFO / I2S | 复用 `audio_demo_core` 的 `sum_to_i16`、深度 1 保持、`audio_transport` |
| 状态/诊断 | deadline、underflow、engine error、voice activity 汇总给 RT |

### 2.2 不应该共享

| 不共享项 | 原因 |
|---|---|
| 每采样系数/状态工作 bank | 两个引擎每采样都要读/写；共享单端口/1W1R 的访问次数不够；本地 bank 才是“每引擎一个端口” |
| 每引擎的 loader/allocator | ENG1 是 2B/2C 的 index+72-bit loader；ENG2 是 7 字段 + A/B bank 装载 |
| 每引擎的激励生成 | ENG1 是 song_player 的升余弦脉冲；ENG2 是 `(q,q̇)` 初值/块激励 |
| 每引擎的内部流水 | 合并会破坏 1508/480 周期和各自的 Fmax |

**一句话**：共享“**时间、系数源、结果、命令、后级**”，不共享“**每采样工作状态和流水**”。

**为什么不是“一个文件全装”**：一个 `synth_top.sv` 可以有 500–800 行，但把

`synth_top` 只做**连线和调度**，每个子块独立文件；板级 `top.sv` 只做 PLL/引脚。
这仍然是“一个顶层文件管理 PLL、时序、输出到 BUF”的目标，只是把细节分块。

## 4. BUF group：系数源可共享，工作状态本地

### 4.1 建议的缓冲区

| 缓冲 | 深度/宽度 | 大小 | 作用 |
|---|---|---:|---|
| `cmd_fifo` | 16 × 64 bit | 1 kbit | RT → 调度器：note on/off、program、control、engine_id |
| `coeff_stage_eng1` | 2 × 48 × 72 bit | 6.9 kbit | ENG1 下一音的 72-bit 系数，双缓冲 |
| `coeff_stage_eng2` | 2 × 48 × 224 bit | 21.5 kbit | ENG2 下一音的 7 字段系数，双缓冲 |
| `x_buf_eng2` | 8 声部 × 64 采样 × 32 bit | 16.4 kbit | ENG2 的块激励；按引擎 X_DEPTH 配置 |
| `result_eng1` | 2 × 64 bit | 128 bit | Q2.30 单采样结果 ping-pong |
| `result_eng2` | 2 × 8 × 64 bit | 1 kbit | 8 声部 YF=40 结果，ping-pong |
| `status` | voice/error/deadline 计数 | 几百 bit | RT 读取 |

合计约 **47 kbit ≈ 3–4 BSRAM**（不含引擎本地 bank）。这比两个引擎的本地
bank（49 + 48 = 97 BSRAM）小得多。**BUF 不是面积/带宽瓶颈，它是控制面邮箱。**

### 4.2 每采样工作状态：为什么不能是一块共享内存

如果让 RT、ENG1、ENG2、POST 都直接读写同一块“数据/结果/系数”RAM：

- ENG1 每采样 4608 次工作缓存访问（3 次/模态 × 1536）；
- ENG2 每采样约 8 × 48 × 11 ≈ 4224 次（7 系数 + 2 状态读 + 2 状态写）；
- 合计约 **8832 次/采样**；2048 周期内需要 **4.3 次/周期**，还不含 RT/POST；
- 两个引擎的端口语义不同（72-bit 单端口 vs 7×32-bit + A/B 双写口），
  共享 RAM 需要 4–5 个 master 的仲裁/多端口，Fmax 和时序都会退化。

**结论**：BUF 只承载“命令、系数暂存、结果、状态”，工作内存留在引擎本地。
这样两个引擎可以并行、各自保持 1508/480 周期和 104 MHz/100 MHz 的本地时序。

### 4.3 仲裁

| 访问 | 频率 | 方案 |
|---|---|---|
| 引擎结果写 | 每采样 1–8 次 | result ping-pong；引擎写 bank n，POST 读 bank n−1 |
| POST 读结果 | 每采样 1 次 | 与引擎写不同 bank，无冲突 |
| RT 命令 | 稀疏 | 单生产者/单消费者 FIFO |
| 系数暂存 | note-on | 双缓冲；RT 写 inactive，loader 读 active，note-on 时切换 |
| 状态 | 稀疏 | 寄存器/小 RAM，RT 读 |

没有高带宽仲裁；最坏情况是 note-on 时 RT 写系数与引擎读本地 bank 同时发生，
但它们访问的是不同存储（暂存 vs 本地 bank），不冲突。

### 4.4 共享系数源（max-width）：可行，而且推荐

你的想法在这一层成立：把系数 BUF 按最大位宽 **224 bit** 做一份，按 `engine` 分 region；
ENG1 只读 `[71:0]`，ENG2 读 `[223:0]`；“另一个 engine 不读”就是 region 隔离。
关键前提：**共享系数 BUF 只在 note-on 装载时读，不每采样读**——每采样的工作副本
仍在各自本地 bank。这样单端口就够。

容量（按当前 3 种 forte 的 123 keys 估算）：

| 方案 | bits | BSRAM @63% | 说明 |
|---|---:|---:|---|
| ENG1 原生 72-bit 表 | 123×48×72 = 425 kbit | ~37 | 现有 A 表量级 |
| ENG2 原生 224-bit 表 | 123×48×224 = 1.32 Mbit | ~114 | 物理引擎表 |
| max-width 共享全表（两 region，各 224-bit） | 2×123×48×224 = 2.64 Mbit | **~228** | 仍 <340，但已经很重 |
| max-width 共享“活动声部工作副本” | (32+8)×48×224 = 430 kbit | ~23–37 | 比原生 196 kbit 多 13–20 块 |
| 只做“下一音暂存” | 2×48×224 = 21.5 kbit | 2–3 | **推荐这个尺度** |

- 全表共享在 123-key/3-forte 下约 228 BSRAM，仍 <340，但已经很重；
  5 种全动态（288 keys）会超过 6.12 Mbit，**不可行**。
- 如果只做“活动声部工作副本”，容量可接受，但 ENG1 每个 entry 浪费 152 bit；
  而且它不能替代每采样本地读（见下）。
- 如果只做“下一音暂存”，21.5 kbit，代价可忽略；这是最划算的复用。
- 端口：note-on 时 ENG1 48 读/音、ENG2 48 读/音；10 音/秒约 960 读/秒；
  100 MHz 单端口完全够；两个 loader 用简单优先级仲裁即可。
- 做法：一个 224/256-bit `coeff_buf`（ROM/RAM），地址 `{engine, key_id, mode}`；
  `coeff_loader_eng1` 读 224 取 `[71:0]`，`coeff_loader_eng2` 读全部；
  写入各自本地 bank。另一个 engine 的 region 不读，符合“另一个不读”。

### 4.5 为什么每采样 state/result 不能共享

| 项 | ENG1 | ENG2 | 合计 | 结论 |
|---|---:|---:|---:|---|
| state 条目 | 32×48=1,536 | 8×48=384 | 1,920 | 64-bit/条，共 123 kbit |
| state 读/采样 | 1,536 | 384 | 1,920 | |
| state 写/采样 | 1,536 | 384 | 1,920 | |
| 合计访问/采样 | 3,072 | 768 | **3,840** | 单端口 3,840 > 2,048；1R1W 1,920 周期 = 93.75%，无余量 |
| result 写/采样 | 1 | 8 | 9 | 小，但可能同拍；每引擎 ping-pong 更简单 |

- **单端口 state RAM 不可能**：3,840 次访问 / 2,048 周期 = 1.875 次/周期 > 1。
- **1R1W state RAM 理论可行**（2 次/周期 → 1,920 周期，93.75%），但两个引擎的
  read/write 必须逐拍交错，且只剩 128 周期余量；任何 note-on/刷新/停顿都会超。
  本地 bank 给 ENG1 4 个 lane 端口、ENG2 7 个字段阵列 + A/B 双写口，天然多端口，
  没有仲裁。
- **容量不省**：共享 state 还是 123 kbit；本地也是 123 kbit。共享只增加仲裁，
  不减少面积。
- **“另一个 engine 不读”对 state 不成立**：两个引擎每个采样都要读写自己的 state；
  另一个 engine 不是空闲的，它也在用端口。只有“另一个 engine 完全不活动”时才成立，
  那就失去了双引擎并行。
- 如果一定要一块物理 state BUF：用**两个 1R1W bank**（每引擎一个）或 true dual-port；
  这实际上就是“本地 bank + 统一 wrapper”，不是单端口共享。

**所以你的 max-width 思路是对的，但要落在“系数源/暂存”这一层；**
**每采样工作状态仍应本地。** 这也解释了为什么“另一个 engine 不读”不能解决
state 的端口问题——它不读系数，但它要读写自己的 state。

## 5. 时序与周期

### 5.1 一个 tick，两个引擎并行

| 项 | 数值 |
|---|---:|
| 核心时钟 | 100 MHz |
| 音频采样率 | 48.828 kHz（实际） |
| 每采样周期 | **2048** |
| ENG1 满载 | 1508 周期 |
| ENG2 8 声部 | ~480 周期 |
| POST body | ~74 周期 |
| 结果/混音 | ~10 周期 |
| RVB（若做） | 视结构，~100–500 周期或流水 |

**关键**：1508 和 480 不是相加，而是跑在不同硬件上（4 lane vs 7 乘法器）。
共享的只有时钟、结果 BUF、POST/RVB、输出 FIFO。ENG1 是慢的那个，
所以 sample deadline 由 ENG1 决定；ENG2 有 1500+ 周期余量。

### 5.2 结果 ping-pong，给 POST/RVB 一个完整采样

不要在 ENG1 的 `out_valid` 后立刻串行做 POST/RVB——那样只有
2048−1508=540 周期，body 74 周期还可以，RVB 很可能不够。建议：

```text
tick n:    ENG1 处理 sample n，写 result bank n%2
           ENG2 处理 sample n，写 result bank n%2
           POST/RVB 读 result bank (n-1)%2，处理 sample n-1
tick n+1:  swap；POST/RVB 处理 sample n
```

这样 POST/RVB 有完整 2048 周期（或至少 1500+），只增加 **1 个采样延迟
（20.48 µs）**。对非实时监听可接受；对实时麦克风监听不适用（但当前 SONG
路径不是实时监听）。

**ENG1-only 例外**：`ENG2_EN=0` 时应让 ENG1 走原有的直接路径（不经过
result ping-pong/mixer），否则 1 sample 延迟会改变启动/欠载对齐，
“与 v5 逐位一致”就不能按原采样序号直接比较。混音/BUF 只在 `ENG2_EN=1` 时插入。

### 5.3 启动/首帧

- ENG1 的 loader 216 周期/音；ENG2 的系数/状态装载也在启动时完成。
- 首帧可能是零/欠载；TX FIFO 的 `underflow_sticky` 记录，稳定后清零。
- `playback_ready` 建议门控在“**首个有效混音结果**”而不是“首个 FIFO 写”；
  否则两个引擎都没启动时也可能先写零帧、提前打开功放。当前实现只检查
  FIFO 写，统一顶层应加一个 `mix_valid`/`engine_started` 条件。

### 5.4 PLL / reset

- 复用 `clock_reset.sv`：两个 PLL 都 lock 后释放 `rst_n`；失锁立即拉低。
- 两个引擎都在 `clk_core` 域；I2S/FIFO 在 `clk_audio` 域；不新增 CDC。
- `core_sample_pulse` 已经是从音频域同步到 core 的单拍脉冲；两个引擎都用它。
- 统一顶层的 reset 要同时清 BUF 的 ping-pong 指针、引擎 bank 选择、POST/RVB
  延迟线；不要在运行中单独 reset 一个引擎而另一个继续写 BUF。

## 6. 输出格式对齐（最容易出 60 dB 错误的地方）

| 引擎 | 输出 | 小数位 | 处理 |
|---|---|---:|---|
| ENG1 | 64-bit `mix_sum` | Q2.30（30 frac） | 保持 |
| ENG2 | 64-bit `y_data` | YW=64 / YF=40（40 frac） | 转 Q2.30：`(y + 2^9) >>> 10`，饱和 |

建议：

1. **统一到 Q2.30**（与现有 body_filter、`sum_to_i16` 一致），ENG2 右移 10 位；
   30 位小数对 16-bit 输出足够，且不改变 POST 的格式。
2. 每引擎先乘一个 **16-bit 增益**（Q1.15），再加；不要先加再统一缩放，
   否则两个引擎的相对电平不可调。
3. 混音用 64-bit 或更宽的保护位；加完后饱和到 Q2.30 的 64-bit 范围，
   不要在每个引擎内部提前截断。
4. 用已知直流/正弦向量验证：ENG1 单独、ENG2 单独、两者同幅同相/反相，
   检查和的幅度/符号；再跑真实音。
5. 如果以后要高精度混音，可以统一到 Q2.40（ENG1 左移 10，ENG2 保持），
   但 POST body 的系数/格式要跟着改；第一版不建议。

**注意**：ENG2 的 `YF=40` 和 ENG1 的 Q2.30 不是“差不多”，是精确的 10 位差；
如果忘了移位，ENG2 会小 60 dB 或大 1024 倍，必须用测试锁住。

## 7. POST 与 RVB

### 7.1 POST

- 复用 `body_filter.sv`：4 段 biquad、Q2.30、valid/ready、74 周期、1 BSRAM、6 DSP。
- 三种模式：
  1. **共享 body**：混音后过一个 body（当前吉他的做法）；便宜，但会把所有引擎
     都染成同一个箱体；
  2. **每引擎 body/bypass**：ENG1 过吉他 body，ENG2 bypass 或过自己的腔体；
     更符合 B 类/物理引擎的音色，但要多一个 body 实例（+1.3k LUT / 1.5k FF /
     1 BSRAM / 6 DSP）；
  3. **可编程 body**：共享一个 body，系数按 engine/class 切换；面积最省，
     但切换时要有交叉淡化/状态清理。
- 建议第一版用 **ENG1 body + ENG2 bypass** 的可配置模式，先把双引擎混音跑通；
  不要默认把吉他箱体套到物理引擎上（B 类文档已建议 B 旁路吉他箱体）。

### 7.2 RVB

当前工程没有 reverb。建议：

- **send/return 干湿混合**，不要 `POST --> RVB` 100% 串行湿声；否则所有声音
  都被混响吞掉，且无法 bypass。
- 简单 Schroeder（4 comb + 2 allpass）或小 FDN；延迟线用 BSRAM；
  估计 +8–16 BSRAM、+2–6 DSP、+1–2k LUT/FF。
- 放在 POST 之后、输出适配之前；`RVB_EN=0` 时完全 bypass，保证 A/B 对拍。
- 混响的延迟线是**采样级状态**，与两个引擎的 sample tick 同域；不要在
  `clk_audio` 域做混响（会引入新的 CDC/延迟）。
- 第一版先留 hook + bypass，不要为了“图里有 RVB”先做一个不可 bypass 的
  串行混响。

## 8. RT / 控制面

### 8.1 当前现实

- ENG1 有 `song_player`（固定 42 事件 ROM）+ `coeff_loader` + `modal_engine`，
  但没有通用 RT 事件队列；`song_player` 是“固定曲目播放器”，不是 MIDI/实时输入。
- ENG2 有 `modal_voice_top` 的装载口和作业口，但**没有 note allocator/loader**，
  也没有真实系数 ROM；`rtl/simsynth/README.md` 明确列为“还没做”。

### 8.2 建议的 RT 接口

```text
RT --> cmd_fifo --> event_router
                     ├─ ENG1: song_player / voice alloc / coeff_loader
                     └─ ENG2: voice alloc / bank loader / frame controller
RT --> coeff_stage_eng1 / eng2 --> 本地 bank
RT <-- status: active voices, errors, deadline, underflow
```

- 统一事件格式：`{engine_id, note_id, midi, vel, dyn, on/off, timestamp}`。
- 每个引擎保留自己的分配/装载逻辑；顶层只做路由和状态汇总。
- `note_id` 用于同音重叠/精确 note-off；ENG1 的 `song_player` 目前是固定序列，
  要做实时 RT 需要新的 allocator；ENG2 也需要一个 8 声部分配器。
- 系数：RT 写 `coeff_stage_*`，引擎在 idle/note-on 时拷贝到本地 bank；
  不要在引擎运行时直接改本地 bank（ENG1 的 `cfg_ready` 只在 idle；ENG2 的
  A/B bank 也是“装非活动份”）。
- 这条控制面是**新增工作**，不是一个 mux 能解决的；建议单独排期。

## 9. 资源估算

以 8 声部 ENG2 为例（当前 `modal_voice_top` 实测）：

以当前 v5 整机为基线，加 ENG2、BUF、RVB 的**增量**（避免把“现有整机”漏算）：

| 块 | Logic | FF | BSRAM | DSP 单元 | 周期/采样 |
|---|---:|---:|---:|---:|---:|
| 现有 v5 整机（P&R） | 15,416 | 8,911 | 52 | 14 | — |
| + ENG2 8 声部 | +1,823 | +816 | +48 | +28 | 480 |
| + BUF/mix/POST 控制 | +1,500 | +1,000 | +3–4 | +0–2 | ~20 |
| + RVB（可选） | +1,500 | +1,000 | +8–16 | +2–6 | 100–500 |
| **8 声部，无 RVB** | **~18.7k** | **~10.7k** | **~103–104** | **~42–44** | max(1508,480)+POST |
| **8 声部，含 RVB** | **~20.2k** | **~11.7k** | **~111–120** | **~44–50** | 流水后 2048 内 |
| **16 声部，含 RVB** | **~22.0k** | **~12.5k** | **~159–168** | **~72–78** | 2 引擎并行 |
| 器件容量 | 138,240 | 139,140 | 340 | 298 | — |

16 声部 ENG2（2 个引擎）：BSRAM +48、DSP +28、Logic +1.8k、FF +0.8k；
含 RVB 约 **160–168 BSRAM / 72–78 DSP / 22k logic**，面积仍然可行。

**面积不是瓶颈，时序才是**：
- ENG1 当前 setup 最坏 +1 ps，没有任何余量；
- ENG2 独立 PnR 104 MHz，只有 4% 余量；
- 统一顶层新增的 BUF/mix/POST 连线和扇出可能把两者都拖慢；
- 必须做 **ENG1-only / ENG2-only / 双引擎** 三次独立 P&R，不能只综合一次就宣布通过。

## 10. 分阶段路线

### S0：契约与 shell（不改音色）

- 定义 `engine_if` / `buf_if` / `result_if`：tick、start/done、result valid、
  Q 格式、每引擎增益、reset。
- 新增 `synth_top.sv`，先只实例化 ENG1 + 现有 body + output；
  `ENG2_EN=0` 时走 ENG1 直通路径（BUF/mixer 旁路），与现生产逐位一致。
- 板级 `top.sv` 改为 `clock_reset + synth_top`；引脚/PLL 不变。

**Exit gate**：ENG1-only 与 v5 逐位一致；资源/时序不低于基线。

### S1：ENG2 独立接入

- `eng2_wrap`：`modal_voice_top` + `modal_engine7` + 每采样帧控制
  （`start/n_samples=1/n_modes=48`，等 `done`，读 8 声部结果）。
- ENG2 仍用自己的本地 A/B bank；不混音，结果只写 `result_eng2`。
- 用 `rtl/simsynth/tb/golden_*.txt` 逐位对拍；先单声部，再多声部。

**Exit gate**：ENG2 8 声部结果与黄金逐位一致；`done` 在 480± 周期内；
ENG1 同时运行不受影响。

### S2：结果 ping-pong + 混音

- `result_eng1/2` 双 bank；每采样 swap；POST 读上一采样。
- `mixer`：ENG2 YF=40 → Q2.30；每引擎 16-bit 增益；64-bit 饱和和。
- 先 `POST_BYPASS=1`，验证 ENG1/ENG2 单独与混合的幅度/符号/延迟。

**Exit gate**：ENG1+ENG2 混音逐位/按已知向量正确；无溢出；单引擎 bypass 正常；
总延迟 = 1 sample（20.48 µs）。

### S3：POST（body/cavity）

- 复用 `body_filter`；`POST_MODE`：shared / per-engine / bypass。
- 第一版 ENG1 body + ENG2 bypass；A/B 对拍时全 bypass。
- 检查 body 的 `valid/ready` 与 ping-pong 的背压；不能丢帧。

**Exit gate**：body 输入/输出与现有单元测试一致；双引擎混音后 body 不溢出；
`POST_BYPASS` 逐位等于 S2。

### S4：RT / loader / allocator

- 统一 `cmd_fifo` + `event_router`；ENG1 保留 song_player 作为固定源，
  ENG2 新增 8 声部分配器和 bank loader。
- 系数暂存双缓冲；note-on 时切换；运行中不改本地 bank。
- 状态/错误/deadline 汇总。

**Exit gate**：note-on/off、同音重叠、满池、reset、错误路径；ENG1 旧歌逐位不变；
ENG2 真实系数（需要先生成）能装载/发声。

### S5：RVB + 板级

- `rvb` send/return；`RVB_EN=0` bypass；先固定干湿/衰减。
- 板级 `top` 参数化；综合/P&R；整链对拍；实板。

**Exit gate**：RVB bypass 逐位；RVB 开时无自激/溢出；整机资源/时序/实板通过。

## 13. 风险登记

| 风险 | 概率/影响 | 缓解 |
|---|---|---|
| 统一顶层时序不收敛 | 高/高 | 三次独立 P&R；接口寄存；BUF 只做邮箱；不要共享工作内存 |
| ENG2 格式对齐错 | 中/高 | 先已知向量；Q2.30 固定；锁定移位/舍入 |
| ENG2 缺 ROM/loader/allocator | 高/高 | 先做引擎独立接入；控制面单独排期；不要假装已生产 |
| BUF 仲裁/死锁 | 中/中 | ping-pong；单生产者/消费者；超时/错误计数 |
| POST 染色 | 中/中 | 每引擎 bypass/body select；A/B 对拍全 bypass |
| RVB 自激/延迟 | 中/中 | 先 bypass；固定衰减；限幅；单独测试 |
| 资源超预算 | 低/中 | 8 声部先做；16 声部/5 种表再评估；RVB 可选 |
| 双引擎 note-on 冲突 | 中/中 | 统一 cmd FIFO；每引擎独立 allocator；固定优先级 |

**一句话总结**：顶层可以统一，但统一的是**时间、结果、命令和后级**，不是两个引擎的
工作内存；BUF 做成“邮箱 + 结果 ping-pong + 系数暂存”，两个引擎保留本地 bank，
