## 1. 实板事实与当前判断

用户报告同一套MAX98357A/3.3V/8Ω接线播放独立持续测试音成功；换回`build/song_synthesis_core100_20261007/parent_core100.fs`后无声，测得SD低、BCLK约3.125MHz、LRC约49kHz、DIN低，时钟稍有过冲。

- 单音成功不等于歌曲版成功，但说明无需先换喇叭/功放或重新猜I2S采样率。
- 若BCLK/LRC确实连续，音频发送器不是长期保持复位。反复复位或间歇锁失仍需捕获，不能凭频率读数完全排除。
- SD低、DIN低与首个PCM未到TX FIFO的状态一致，但SD还受锁定/复位门控；不能仅凭这四个读数断言内部具体故障。
- 不将SD强制拉高来掩盖首样本缺失，不绕过箱体/装载或改变算法来“先响”。

## 2. 已完成的静态review

1. 当前工作区与实际core100构建输入核对：28个RTL/IP/ROM/CST/SDC/源清单匹配。`board_top`按original_sha核对，原构建的ROM绝对路径重定位记录保留；SDC忽略注释后有效命令相同。
2. 第一歌曲事件为guitar/MIDI60/forte；索引地址121，word=`B648B`：present=1，n_modes=27，offset=1163，系数ROM5483项。原始数据确实有此音，不据此声称实板ROM读值已验证。
3. 实际编译wrapper启用guitar箱体，32声部×48模态，100MHz核心/12.5MHz音频，不改变任何参数。
4. 音频帧节拍通过`audio_transport`跨域后进入`song_player.sample_tick`，这是首个装载请求的前置条件。
5. `song_player`的`S_LOADW`只等`load_done`，不消费引擎错误反馈；装载失败可能留下永久等待。这里只指出故障表现，不立即修改恢复策略。
6. 引擎结果先经song_player的单拍输出，再经箱体和PCM暂存进入TX FIFO。不能只检查引擎out_valid就宣称后级已收到。
7. `playback_ready`只检查`core_tx_valid && core_tx_ready`，不检查数据非零；需单独观察是否有非零PCM进入FIFO。
8. 几个关键完成/错误事件只有一个100MHz时钟周期，不能直接用万用表或普通长时基观察，应先锁存。

结论：已确认观测位置与握手条件，**尚未确定实板卡点**。下一步增加只读观测，不重新推导或优化冻结核心。

## 3. 四根调试线与测量方式

用户已授权使用PMOD2剩余四根针脚。原理图核对结果如下：

| 位 | 丝印/FPGA管脚 | PMOD2信号 | J26原理图针号 |
|---|---|---|---|
| bit0（最低位） | B21 | IO4 | 12 |
| bit1 | A20 | IO5 | 10 |
| bit2 | A19 | IO6 | 8 |
| bit3（最高位） | A18 | IO7 | 6 |

拟采用3.3V LVCMOS输出，仅接示波器高阻探头/万用表，不连接其他输出或外加电源。其余MAX接线不变。

四位组合读取顺序为`A18 A19 A20 B21`。例如`0101`=十进制5：A18低、A19高、A20低、B21高。示波器若设CH1=B21、CH2=A20、CH3=A19、CH4=A18，则按CH4..CH1读码。

上电/下载后等约2秒再读。拟在核心复位释放后用100MHz计数约1秒，捕获此前事件并锁定报告码；不依靠外部按键触发观察窗。

报告码是**启动窗口内的进度快照**，不是持续运行认证；如果其后才出现故障，需另做后续采集。重复下载可重新观察，勿用RECONFIG加载Flash旧程序。

## 4. 拟观察的阶段和代码

拟在核心时钟域为每个事件设置sticky位，记录启动窗口内是否发生；有ready的接口按真实握手记录。下表为待实现编码，不是现有bitstream功能。

| 码（hex） | 拟报告含义 |
|---|---|
| 0 | 观测复位/启动状态；可能未释放或未运行，不能单独区分复位与核心无时钟 |
| 1 | 核心观察窗完成，未见音频采样节拍 |
| 2 | 见节拍，未见load握手 |
| 3 | load已握手，未见load_done |
| 4 | load_done已见，未见engine输出；采样请求/计算需下一轮细分 |
| 5 | engine输出已见，未见箱体输出；song输出/箱体入口需下一轮细分 |
| 6 | 箱体输出已见，未见TX FIFO写握手 |
| 7 | TX FIFO已有写握手，但启动窗口只见零PCM |
| 8 | 非零PCM已进入TX FIFO；仍不代表FIFO读侧/I2S或喇叭验收通过 |
| 9 | 锁存到body_coeff_error；不能把这一标志当作所有实板ROM损坏的检测器 |
| A | 引擎错误1：voice越界 |
| B | 引擎错误2：缺失ROM索引条目 |
| C | 引擎错误3：ROM元数据非法/范围越界 |
| D | 引擎错误4：激活了未成功装载声部 |
| E | 引擎错误5：内部bank错误 |
| F | 保留给观测逻辑检测到的进度不一致等异常，细则在实现前明确 |

错误码优先于进度码；引擎错误只在`engine_error_valid=1`时锁存，保存窗口内首个错误。窗口末拍出现的事件必须计入本次快照。复位清掉本次观察，但不据此推断实板复位极性已正确。

必须记录的原信号：

- `core_sample_pulse`
- `sp_load_valid && sp_load_ready`
- `sp_load_done`
- `sp_sample_valid && sp_sample_ready`（辅助记录）
- `sp_engine_out_valid`
- `sp_out_valid`（辅助记录）
- `body_src_valid`、箱体系数状态（ENABLE_BODY=1）
- `core_tx_valid && core_tx_ready`
- 上述FIFO写握手同时`core_tx_data != 0`
- `engine_error_valid/engine_error_code`

辅助记录用于核对进度一致性/后续进一步定位，不把未观察到的阶段伪装成已经通过。

## 5. 如何加观测而不改冻结实现

- 放在独立`song_debug`工程，原歌曲版、已出声测试音和冻结快照均保留。
- 原`rtl/core/`、`song_player`、`audio_transport`、FIFO、I2S、PLL保持byte不变。
- 不使用未经验证的跨模块层级引用作为综合方案。需要引出集成层内部信号时，在独立目录生成`audio_demo_core`的调试副本，仅增加观测端口/只读连接；用自动差异检查验证删去这些增加项后与冻结原文一致。
- 不改变激励、系数、状态更新、valid/ready、复位策略、BODY使能、时钟频率或周期调度。诊断计数和锁存位不反向参与原链路控制。
- 用新顶层传递调试端口，保持原时钟/复位/I2S层级尽可能一致，以便审查SDC对象是否仍正确命中。
- 增加观测会改变综合/布局/扇出；**数值等价不等于物理时序相同**。必须重新检查真实构建，不假定原setup约+2ps可以原样保留。

## 6. 实现后必须亲跑的验收

1. **观察器单测**：全部进度码、每个错误码、错误优先级、单拍事件、窗口末拍、窗口后锁定、复位重启，以及非法进度组合。
2. **真实链路对拍**：冻结原集成与观测副本使用同样的真实engine/body/ROM，比较至少256个完整PCM/I2S帧及握手/错误行为；观测版不能改变原输出。PLL在功能仿真中使用测试时钟模型，声明边界。
3. **故障注入**：测试环境中模拟节拍未到、缺失第一索引、引擎未完成、箱体未出结果、FIFO写不接收等，验证报告指向预期阶段。只在测试bench/临时夹具注入，不污染真实ROM或生产RTL。
4. 仿真为缩短耗时可只缩短**观察窗**，不降声部数、不改NOTE_GAP、不降频或改变原算法；同时验证真实1秒参数的计数边界。
5. **真实Gowin综合/P&R审查**：四新管脚真实映射/电气、源和ROM存在、PLL实际参数、约束有效/对象命中、setup/hold/MPW及未约束路径。新增调试输出应有符合高阻异步测量用途的明确延迟预算，不用blanket false-path切核心状态路径。
6. 确认生产输入SHA未变；诊断.fs、README、报告和SHA放独立build目录，不覆盖两份旧.fs。不调用Programmer，不写Flash。

原主工程MPW/PLL模型未放行状态保持。新工程若有时序违规，必须明确报告并处理/请求决定，不因为是“调试用途”自动宣称验收通过。
