## START成功但无音符回传的继续排查（2026-11-02）

现场反馈为：网页显示正在录制；按下/松开PAD正常发声；RX计数不增加；停止后提示没有回传。这个现象不能直接归因于下节的永久隔离。START回复只能证明配置请求/回复走通，尚不能证明TYPE82录制流到达；PAD音频也独立于UART回传。

本轮发现并修复两处上位机观测问题：

- `recording-ui.mjs` 原先只要START成功ACK就显示“正在录制”。现要求当前录制ID的TYPE82起点和START ACK都到达，顺序任意；ACK后2秒仍无起点则明确报错并尝试STOP。空take单独提示“收到起点但没有音符事件”，不与没有任何录制流混为一谈。保留帧/NoteOn/NoteOff/忽略帧/结束帧及错误原因等诊断。
- `serial.mjs` 为避免每个TYPE82触发全UI刷新，跳过了onState；`rxFrames`内部虽递增，界面数字却可能一直停在上次配置回复。现以250ms周期刷新计数，鼠标悬停RX可查看原始字节/录制帧/解码错误计数。计数冻结本身不能作为“板端没发字节”的证据。

连接面板新增“导出通信诊断”，输出 `midi-link-diagnostic.json`：包含原始TX/RX字节（合计最多8192B、128块）、CRC/帧解码错误、录制ID及本次录制统计、配置回复payload和日志。RX字节在FrameReader校验前记录，因此被CRC/长度/SLIP校验丢弃的内容也可以复查；录制ID不匹配会计入ignoredFrames并保留lastIgnoredId。导出后可区分链路无原始字节、收到损坏帧、收到其它take的帧、起点正常但没有音符等情况。

补充了此前没有执行的完整板级路径验证：`sim/unit/board/tb_instrument_board.sv` 的UART BFM/解码器现可通过UART_BAUD参数切换，默认加速速率保留；新增 `sim/run_record_uart.py` 使用Verilator运行生产板级录制路径，默认实际115200波特率，仅PLL/ADC/Flash采用既有模型。覆盖真实START/STOP配置回复、ADC/PAD→router快照→capture→transport→UART引脚、END先于STOP ACK、STOP重试及此前的线路故障恢复。

## 有线UART故障隔离与录制回传恢复（2026-11-02）

确认源码死锁：生产板 `session_restart=0`，有线没有 `connect_event`，物理 framing/break/overflow 会置隔离，却无法置 `restart_pending`；`capture_enable=0` 后网页重开串口也无法恢复。已在 `comm_top` 为有线增加双触发同步和连续高电平计数，隔离后连续空闲32个位时间才提供恢复资格（50MHz/115200时13920拍，约0.2784ms）。低电平或新物理错误重新计时，持续break和普通停止位均不能解隔离。

`session_ctrl` 将该资格作为显式restart之外的有线恢复入口，仍等待该来源事件排空、业务idle、cleanup完成、仲裁器及解析器退休，再单拍清除该来源配置缓存并flush链路。恢复资格是实时电平，清理未完成时再次出现低电平，不能沿用旧资格。错误sticky/count保留。网页v1选择固定115200，切回v1也会覆盖其它速率选择。

新增 `tb_session_recovery`、`tb_comm_recovery`，并加入默认通信回归。集成测试通过真实UART引脚制造低停止位、持续break和解析器阻塞后的RX FIFO溢出，覆盖延迟业务完成、噪声打断空闲、重复故障、无旧事件/回复泄漏、配置缓存清除与另一来源缓存保留、恢复后MIDI及完整START→ON→OFF→ON→END回传。将会话释放条件临时恢复成原条件后，新单元测试在automatic retirement/cache reset处失败，证明能捕获原问题。

本机使用临时解包的Verilator 5.048运行，未安装系统软件包。`sim/run_comm.py` 增加 `--simulator verilator`，保留默认iverilog入口；现有RTL的默认input等语法不被此次取得的Icarus11支持。运行产物保存在指定 `--out` 目录。

### 确认的问题

#### W1：混响干湿乘法在移位前截断（历史F09仍存在）

`rtl/router/routers/reverb_router.sv:156` / `:157`：

```systemverilog
dry_w <= (xd[3] * gd) >>> G_FRAC;
wet_w <= (wet * gw) >>> G_FRAC;
```

目标69位使乘法表达式也只保留69位，而64×32完整乘积需要96位。移位在截断之后发生，末端饱和不能恢复丢失的位。直接用生产NONE路径复现：

| 输入整数 | 当前输出 | 正确输出 |
|---:|---:|---:|
| 2^24 | 2^24 | 2^24 |
| 2^40 | 2^40 | 2^40 |
| 2^41 | -2^41 | 2^41 |
| 2^42 | 0 | 2^42 |
| -2^42 | 0 | -2^42 |

NONE的正输入从2^41开始越过乘积符号边界。2^41在F24下是实际幅度131072，远大于PCM归一化满幅1；这个边界复现不能证明当前正常音乐实际达到该范围，不能直接归因当前小音量。

#### W2：梳状混响反馈与加权乘法同类截断

`rtl/router/parts/comb_reverb.sv` B级的四条 `fb<=s*g>>>27` 目标64位、四条 `t<=s*w>>>27` 目标69位，都未显式保留96位中间乘积。对N=8、延迟2/3/4/5、g=0.5、w=0.25的真实RTL测试：

- 输入脉冲2^24：48样本与无界整数参考全部相同。
- 输入脉冲2^38：反馈尾音23个样本不符。例如第16样本期望103079215104，得到68719476736。
- 输入脉冲2^44：反馈/加权路径26个样本不符。

仍是大信号范围缺陷，未宣称普通演奏已触发。当前实用范围的通过与完整signed64接口声明的正确性需要分开。

#### W3：加权求和的饱和方向取错位（潜在缺陷）

`comb_reverb.sv` 的sum4是signed71位，越界方向却取 `sum4[63]`，正确方向应取宽和的符号位 `sum4[70]`。独立强制内部加权项复现：

| 宽和 | 正确饱和 | 当前结果 |
|---|---|---|
| +2^63 | +2^63-1 | -2^63 |
| -2^63-1 | -2^63 | +2^63-1 |

此探针主动设置内部t1/t2等项，检查的是饱和电路本身。当前W2截断限制了t的实际范围，因而在现有未修复乘法路径上掩盖了这类大幅求和；不能把内部强制探针描述成当前普通输入已经触发的故障。修复W2后尤其要一起修复并验证W3。

### 修复方向（本次未实施）

- 反馈结果保留足够的高位；必要时先饱和到64位，再与输入用65位加法饱和。加权结果保留69位、四路用71位求和。

## 早期音量追加构建

**历史隔离构建，当前不采用headroom=-1。**

用户要求相对上次实测通过版本继续提高 12dB。板级 `PCM_HEADROOM_BITS` 从 1 改为 -1，PCM 换算右移从 10 位改为 8 位，未限幅信号增益为原来的 4 倍（+12.041dB）。相对最初 headroom=3 的板级版本累计约 +24.08dB。

## 两项条件逐路径复核（2026-11-02，未修改RTL）
