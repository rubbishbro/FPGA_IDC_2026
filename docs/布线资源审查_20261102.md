# 布线与资源审查（2026-11-02）

审查对象：`99762fbe`，工作区 RTL 未修改。本报告比较历史实测网表、11月2日旧诊断及当前代码；资源数字的版本和统计阶段分别标注。

## 结论与证据边界

当前最值得排查的是存储被实现为寄存器加大规模选择树、16声部并行算术，以及高扇出复位/CE和宽总线的跨区域连接。不能仅凭 LUT/FF 总利用率认定器件放得下就一定布得通，也不能把最大模块直接认定为失败网络所在。

仓库实际可读取的最近整板物理报告为 `build/fmap_display_20261101/implementation/instrument_board/impl/pnr/`：已完成布线与位流生成，Logic 75,623/138,240（55%）、FF 34,928（含IO FF）、CLS 52,577/69,120（77%）、BSRAM 151/340（45%）、DSP物理资源172/298（58%）；setup/hold违反端点均0，core Fmax 51.922MHz。PRIMARY/LW均8/8，且有PR1014输入时钟使用普通布线的警告。

`docs/调试记录.md`另记载 `build/pnr_20261102` 的349条未布通网络、CLS84%、复位扇出14859。但本次工作区不存在该目录及 `build/single_play_table`，所以这些只能标为既有记录，不能冒充本轮读取了失败网表、拥塞坐标或未布通网清单。历史成功说明设计曾能布通，不能证明当前源已通过。

## 仍需处理的资源热点

### [P1] 当前LED灯效形成显著FF/MUX热点，原来的低资源判断已经过时

本轮实测`pad_led_effects`为4039FF、2193LUT+768ALU、1390MUX、13个RAM原语；`led8x8`另有1589FF。两者合计5628FF，占整板15.4%；灯效自身占整板级联MUX的24.6%。此前若只看旧led8x8的372FF就认为LED开销可以忽略，已不适用于当前系统。历史网表不存在同名pad_led_effects模块，不能伪造同模块“0→4039”的纯优化对照。

`rtl/drivers/pad_led_effects.sv:65–66,104–108,156–161` 分别保存16槽pending记录、wave记录、整帧snapshot以及64×24位framebuffer；139–140、180–186、217行按可变索引读取，形成选择树。`rtl/drivers/pad_driver.sv:62,99,111–112` 再保存一份1536位gram并做串行读出。两帧缓存用来隔离渲染与发送，不能未经调度分析直接删一份。

建议首先把framebuffer的R_FILL读取改成提前一拍预取的同步RAM，保持`cr.clk_en`消费时数据稳定；再考虑将gram按64×24像素组织、同步读取后24位局部串行化，而非对1536位packed向量动态选位。pending/wave/snapshot读也可利用现有FSM等待状态集中成同步读口；wave_birth_age当前16路并行退休检查须单独处理，不能简单把多读口表硬套单口RAM。最后才评估合并帧缓存，保留BOOT_FILL、led_busy及displayed_phase/tx_phase的实际显示时刻合同。

### [P1] FFT峰值表与平滑表仍保留寄存器/选择树结构

`FFT_spectrumshow/src/display/lcd_fft.v:348` 的dot_ram和fall_ram共2560个RTL存储位，373–396行根据bar_idx组合读取并更新。顺序清零仅删除复位需求，不满足同步BSRAM读模板；尤其dot_ram还直接参与每像素绘制。历史lcd_fft实测1785LUT、1020MUX、2217FF、0RAM，故“顺序清表已解决所有资源问题”不成立。

`FFT_spectrumshow/src/spectrum/spectrum_map.v:45` 更明确强制smooth_ram使用registers：128×10=1280位。118行读取、144行写回，历史模块1278LUT、600MUX、1420FF。这是为规避Gowin不支持的WRITE_MODE而保留的实际折中，不能只加block_ram属性强行解决。

建议先将峰值/计数读出提前到每柱的预取阶段，以当前柱寄存器参与比较和绘制，再独立同步写回；覆盖倒扫、首末柱、冷/热复位和读写同址。平滑表改用独立同步读写always块或器件支持的SDP模板，保留先读后写语义。其时序/颜色/柱索引延迟需一起对齐。

### [P1] 激励的运行时移位、40位相位和多分支算术被复制16份

`rtl/router/parts/excitation.sv:74–75,107–203` 在循环内为每声部生成相位加/减/比较、计数器、衰减加减与状态选择。134/151行的SHIFT和165行的RISE_SH都是输入信号，动态移位需要选择网络；99/104行常数移位才主要是连线。“没有乘法器”不能推出“资源少”。历史excitation_gen为7921LUT+3136ALU、1649FF，算术逻辑开销比其FF数量更突出。

优先评估把有限音色移位配置变成可证明等价的少数选择；其次评估逐槽调度、共享加减/移位通路。主音频帧约1024core拍，16槽存在时分复用的研究空间，但必须重新安排xmap_valid/part_tick消费、一次性发布整帧，并量测最坏调度预算。不能直接把for循环改为多拍后仍保留原立即有效握手。

### [P1] 包络每槽独立32位算术/比较，复位和节拍同时覆盖整组

`rtl/router/parts/envelope.sv:55–97` 每个声部都拥有attack加法、release减法、decay减法、32位比较和多级条件选择，clk_en时整组更新。历史envelope_ADSR为4658LUT+2032ALU、1104FF。新包络已修改比较实现，历史数字只能帮助定位，当前数量见本轮综合对比。

建议与激励统一评估逐槽处理，保存每槽反馈状态，在完整处理后提交emap/dead。不要通过直接取消lvl或acc的初始化来省复位：它们会被反馈消费，必须保留清槽/首次写入及握手合同。

### [P1] 高扇出复位/CE仍需按当前网表重新度量

`rtl/router/voice_router.sv:337–350` 的part_tick，以及激励/包络的clk_en、xmap_valid、整组快照等连接大量端点。`voice_router.sv:967–971` 的S_CFG仍在一拍清空全部active_play数据；单表化只是消除了成功提交沿的另一笔广播。

复位数据拆分已经实施一部分，但current reset网络究竟减了多少必须看工具输出；不得把RTL位宽相加当作综合网表扇出变化。不要把所有FSM、CDC指针、有效链一起迁移GSR；不要把CLEAR换成同样规模的逐位rst_n使能。优先拆无效时不被消费的数据，保留控制/反馈初始化，并按局部消费者布置控制副本；最终核对复制是否被工具合并。

### [P2] 混响的宽乘加和公共系数跨DSP连接

`rtl/router/parts/comb_reverb.sv:48–55,118–125,188–206` 有四路反馈与四路输出乘积；`rtl/router/routers/reverb_router.sv:162–169` 再做两路干湿混合。64×32完整乘积经缩放仍保留69位，另有70/71位加法与饱和。历史comb_reverb为24个DSP原语、1922LUT+1435ALU；不能将“24个DSP原语”直接等同物理报告的DSP资源单位。

建议在完整样本周期预算内时分复用乘法器/加法器，并让系数、操作数寄存器靠近对应DSP。保留反馈读写延迟、复位清扫、clear优先级、96位乘积与最终饱和语义；未经数值范围证明不要直接截成32位来换资源。该模块曾在不同布局中变成临界路径，不能据此判断它是349条失败网络的根因。

### [P2] 双bank各含eng0/eng1，两种互斥只影响运行，硬件都存在

`rtl/router/routers/eng_router.sv:73–113` 实例化两个引擎并MUX输出，`voice_router.sv:500–521` 又各实例化到A/B两bank。历史每个eng_router约807FF、17个DSP原语；两套bank合计四个具体引擎。start门控不消除另一套运算硬件。这是双算法与吞吐需求的架构成本，不是综合器重复错误。

如要进一步共享需从整帧最坏拍数算起。16槽、64模态若仅保留一个每拍一模态的引擎，单纯模态计算已需1024拍，尚未计启动、流水排空与后处理，不能无预算地合并双bank。

### [P2] 新增两个邮箱仍缺少与view邮箱对等的显式CDC路由预算

`FFT_spectrumshow/src/ui/sidebar_system.sv:166–173` 的u_guide_cdc/pixel_guide及`rtl/platform/tang_mega_138k_pro/temporary_fmap_display.sv:27–49` 的u_snapshot/numbers确实存在；当前SDC主要只点名u_view_cdc/pixel_view及FIFO。request/ack首级和稳定payload捕获未得到同类显式max_delay/hold处理。

握手本身不能替代布线时延预算，相关时钟的默认同步时序也不等于已经声明正确的CDC合同。它可能增加无意义的跨域时序优化压力，亦属验收遗漏，但尚不能认定是布线失败主因。后续按实际优化后名字查询首级和数据捕获端点、核对覆盖数量，再补精确约束；不能给整个时钟域加false_path。

## 建议实施与验证次序

1. 保留当前源/约束哈希与综合输出，先用同一份网表进行物理实现，导出真正未布通net、端点位置和拥塞图。失败基线若无法获取，不能给349条网络做模块归因。把“未布通”“布通但setup失败”“reset recovery/removal失败”分开记录。
2. 如果新曲线网表已显著降MUX，先验证这一版能否布通；不要同时重构所有音频模块而失去可比较基线。固定目标core50MHz/pixel33.333MHz，单独比较place/route策略，资源复制选项也应只作为独立实验变量。
3. 后续资源优化优先级：LED缓存/可变索引存储 → 激励动态移位/逐槽调度 → FFT峰值表与smooth_ram的同步存储 → 包络共享算术 → 混响共享DSP。保留16声部、64模态、帧快照及全精度合同；不能靠减少声部或截位来宣称同功能优化成功。
4. 每次仅改变一块，核对LUT、ALU、MUX、FF、BSRAM、DSP、控制网负载和物理CLS。功能测试通过后再跑完整PnR；最终检查setup/hold/recovery/removal/min-pulse-width和显式max_delay，不能只看生成FS或综合Fmax。

资源数字口径：下表LUT为综合网表LUT1..4原语数，MUX为MUX2_LUT5..8级联原语数，后者反映宽选择树，不应与LUT直接相加当作逻辑总利用率。ALU单列；模块统计含子模块，所以父子行不能重复求和。RAM/DSP原语数不直接等于物理报告按器件容量折算的资源数。综合结果可确认映射和资源变化，不能证明布局布线或实际时序通过。
