# ENG1 架构梳理（2026-10-20）

> 目的：把 engine 这部分**从零重新讲一遍**，并给出“现在有哪些东西 / 哪些是遗留 / 收敛到哪里”的清单。
> 旧版 `ENG1_数据处理架构.md` 已归档到 `docs/archive/2026-10/ENG1_数据处理架构_旧版.md`，它只描述 A-only E1，已落后于 RTL。

---

## 0. 一句话

**ENG1 = 32 个 voice × 最多 48 个模态的 TDM 谐振器阵列。**

A/B/C 的差别只有三件事：

1. **表怎么选**（A/B/C 各自的 index/coeff/control/seed）；
2. **x 怎么来**（A 是 7 点脉冲，B 是 NCO×AR×vel，C 是 0 + seed）；
3. **运行期有没有额外动作**（B 有 a1 刷新，C 有 timer/choke）。

**递推核心只有一套**：

```text
y[n] = G·x[n] − a1·y[n−1] − a2·y[n−2]
```

所以 engine 不该有“三套引擎”，只该有“一套 bank + 三种装载/激励/生命周期”。

---

## 1. 一个 voice 到底是什么

一个 voice 是一个槽位，里面放：

| 每 voice | 内容 |
|---|---|
| `class` | 0=A，1=B，2=C |
| `n_modes` | 这个音实际用几个模态（≤48） |
| `control` | 256-bit，B/C 用；A 为 0 |
| `theta_base` | B 用，UQ2.14 的基准 θ |
| `loaded` | 是否装载完成，未完成不能进 `active_mask` |

每个 mode 放：

| 每 mode | 内容 |
|---|---|
| `G, a1, a2` | 72-bit 系数 |
| `y1, y2` | 64-bit 状态 |

存储位置：

- 系数和状态都在 **4 个 lane 的本地 RAM** 里（`poly_modal_lane`）；
- 原始表在 ROM / BUF；
- 每采样每个 voice 只有一个 `x`，广播给它的 48 个 mode。

## 2. 四条流（先记这个，再看代码）

### ① 装载流（note-on 时发生，偶尔）

```text
event(class/layer/inst/note/vel/note_id)
  → index 查表（n_modes / offset / present）
  → 校验（present、n≤48、offset+n≤depth）
  → clear（只清 state_valid，不擦系数）
  → burst 读 core/control/seed（1 词/拍）
  → 写 bank（cfg/seed）
  → commit（control、class、theta_base、n_modes 生效）
```

关键契约：**先校验后 clear**；失败不能动旧声部；commit 前 voice 不可用。

### ② 激励流（每采样）

```text
A: song_player 的 7 点升余弦脉冲
B: NCO 相位 + AR 包络 × velocity
C: x = 0（靠 seed 的 y1/y2 振铃）
        ↓
   x_vec[voice]（32-bit Q2.30，每 voice 一个）
```

A 的脉冲是 `case`/LUT，不占 BSRAM；B 的 NCO/AR 是每 voice 寄存器；C 没有激励表。

### ③ 递推流（每采样）

```text
for each active voice:
    4 个 lane 并行，每个 lane 处理 k%4 == lane 的 12 个 mode
    每个 mode：acc = G·x − a1·y1 − a2·y2
              ynew = round/sat(acc)
              写回 {y1,y2}
              累加 partial_sum
    voice_sum = Σ 4 lane
mix_sum = Σ voice_sum
```

一次只算一个 voice，四个 lane 并行算这个 voice 的不同模态，属于 **TDM**，不是 32 个 voice 同时展开。

### ④ 结果流

```text
mix_sum (Q2.30, 64-bit)
  → body_filter（A 箱体；B/C 旁路）
  → sum_to_i16（衰减/舍入/饱和）
  → audio_transport FIFO → I2S
```

## 3. 当前实际调用树（audio 路径）

`rtl/audio/audio_demo_core.sv` 是**真正接到 I2S 的顶层**：

```text
audio_demo_core（默认 NUM_VOICES=8）
├─ song_player
│    └─ A 的 7 点脉冲 + active_mask + x_vec
└─ modal_engine（默认 USE_BC=0，只编 A）
   ├─ class_loader_mux
   │  ├─ class_loader      （A）
   │  └─ class_loader64    （USE_BC=0 时被 generate 掉）
   └─ modal_poly_bank
      └─ poly_modal_lane × 4
```

注意：

- `audio_demo_core` **没有** `load_class`、`b_*`、`c_*`、`a1_*` 端口；
- 它例化 `modal_engine` 时也没接这些端口；
- 所以 **B/C 目前不在真实音频路径里**，只在 `synth_top` 的测试路径里。

## 6. 为什么现在感觉乱（7 条）

1. **两条链并存**：`audio_demo_core → modal_engine`（A-only）和 `synth_top → eng1_voice_top → modal_engine`（A/B/C）没有合并。
2. **三层壳**：`synth_top` → `eng1_voice_top` → `modal_engine`，load/result 端口在三层重复一遍，改一个信号要改三处。
3. **两套 loader + 一个 mux**：A 与 B/C 的 index/control/seed 语义不同，`class_loader_mux` 用单 bit `class_r` 选输出，边界容易错。
4. **class 行为分散**：loader 选表、`b_x_pool` 选 x、`b_a1_engine` 选 a1、`c_voice_timer` 管 C；没有一个 `voice_runtime` 统管，导致 Control/θ/class 到处传。
5. **两套 bank/lane**：`modal_bank`/`modal_lane` 与 `modal_poly_bank`/`poly_modal_lane` 并存，名字也分不清谁生产。
6. **BUF 不是真 BUF**：`synth_buf` 按 `COEFF_DEPTH × 256` 全深度存，默认 `USE_BUF=0` 时 loader 根本不读它；`eng2` 还 tie-off。它现在是“占面积但不参与”的状态。
7. **文档落后**：旧 `ENG1_数据处理架构.md` 说 B/C 还是目标态，实际 RTL 已经有 B/C；`rtl/synth/README.md` 又说“迁移中”。三份说法不一致。

## 7. 收敛目标

### 7.1 唯一引擎顶

按已冻结的选择，**`synth_top` 是唯一引擎顶**：

```text
audio_demo_core（板级：body/i16/transport）
└─ synth_top（引擎顶：start/busy/done、rd_*、BUF）
   ├─ eng1_voice_top（A/B/C）
   │  └─ modal_engine
   │     ├─ class_loader_mux（→ A / B/C）
   │     ├─ b_a1_engine
   │     └─ modal_poly_bank（4 lane）
   └─ eng2_voice_top（后续）
```

`audio_demo_core` 只保留板级职责，不再直接例化 `modal_engine`。

### 7.2 一个 voice_runtime

把现在散在四处的每 voice 运行态收进一个模块：

```text
voice_runtime
├─ control（256-bit）
├─ class / theta_base
├─ B：a1 刷新请求、NCO/AR 参数
└─ C：timer/choke
```

`b_x_pool` 只读 runtime 的 control，不再自己解析一份；`b_a1_engine` 也从 runtime 取 θ/class。

### 7.3 一个 loader 对外

目标不是保留三个模块，而是：

```text
eng1_loader
├─ A backend（class_loader）
└─ B/C backend（class_loader64）
```

对外只有一套 `load_valid/ready/done`、`clear/cfg/seed`、`commit`；class 选择在 loader 内部，不再有 `class_loader_mux` 这一层。

### 7.4 BUF 只做暂存

`synth_buf` 现在：

```text
ENG1: 5483 × 256-bit = 171 KiB
ENG2:  768 × 256-bit =  24 KiB
```

但 ENG1 只需要 72-bit：

- 若 BUF 存全表：`5483 × 72 = 48 KiB`；
- 若 BUF 只是暂存：`2×48 × 72 = 6.9 kbit`。

建议先按“暂存层”修：`ENG1_DEPTH=2×48`、宽度 72；ENG2 用 224。不要用 256-bit 去装 72-bit 的 ENG1 数据。

### 7.5 遗留清理

生产路径只保留：

```text
rtl/core/：modal_engine, class_loader, class_loader64,
           modal_poly_bank, poly_modal_lane,
           b_voice_ctrl, b_x_pool, b_a1_refresh, b_a1_engine,
           c_voice_timer
rtl/synth/：synth_top, eng1_voice_top, synth_buf
```

以下移到 `legacy/` 或删除（先不删测试）：

- `coeff_loader.sv`
- `modal_bank.sv`
- `modal_lane.sv`

`rtl/simsynth/` 保持只读参考，不参与生产。

## 8. 分阶段做，不要一次性重写

| 阶段 | 动作 | 行为变化 | 验收 |
|---|---|---|---|
| P0 | 本文档 + 模块清单 + 标记遗留 | 无 | 文档评审 |
| P1 | `audio_demo_core` 改例化 `synth_top`；A 路径接通 | A 应逐位不变 | e01–e07 + 音频 A 回归 |
| P2 | `synth_top` 里去掉 `eng1_voice_top` 的重复端口（能合则合） | 无 | 同 P1 |
| P3 | `class_loader_mux` 并入 `eng1_loader`；A/B/C 单口 | 无 | B/C loader 单测 |
| P4 | `voice_runtime` 收拢 Control/θ/a1/C timer | 无 | `test_engine_bc` / C 测试 |
| P5 | `synth_buf` 改暂存宽度/深度；`eng2` 再说 | 无 | BUF 测试 + 资源对比 |
| P6 | 删/归档遗留 `coeff_loader`/`modal_bank`/`modal_lane` | 无 | 全回归 |
| P7 | 单一文档 + 图；旧文档归档 | 无 | 文档检查 |

**P1 是关键**：只要 B/C 还没接进 `audio_demo_core`，engine 就永远是“两套东西”。

## 9. 需要拍板的三件事

1. **板级 top 用哪个？**
   - 推荐：`audio_demo_core` 只做板级，例化 `synth_top`；`synth_top` 是唯一引擎顶。
   - 备选：`synth_top` 直接做板级顶（要把 body/i16/transport 也搬进去，不推荐）。

2. **loader 保留三个模块还是合成一个？**
   - 推荐：对外一个 `eng1_loader`，内部保留 A/B/C backend；`class_loader_mux` 逐步消失。

3. **先做行为不变的结构收敛，还是直接重写？**
   - 推荐：先 P1–P3（行为不变，A 逐位回归），再 P4–P5。直接重写会把 A 的逐位基线弄丢。
